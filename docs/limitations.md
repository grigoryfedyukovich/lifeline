# Limitations

Lifeline 0.1.1 is intentionally conservative and bounded.

## Unsupported or approximate cases

- Indirect calls through interfaces, reflection, arbitrary function values, and generated dispatch are not resolved.
- Same-package direct goroutine targets are inspected only when they are within `max_functions`.
- Vet mode may use a compatible direct-function fact for a cross-package target. Standalone mode does not import those facts. As of this release this asymmetry is disclosed rather than silent: a standalone run that hits a cross-package target reports it under "goroutine target(s) could not be analyzed" in the clean-result summary (text) or `coverage.unsupported_targets` (JSON/SARIF), instead of indistinguishably reporting "no lifecycle diagnostics."
- Unsupported target bodies are retained as model evidence and are now surfaced in the report as coverage information (text: listed under a clean result; JSON/SARIF: `coverage.unsupported_targets`). They are informational, not diagnostics: they carry no rule ID, cannot match `-fail-on`, and are excluded from the pass/fail decision — a goroutine whose body could not be inspected is neither a finding nor proof of correctness.
- The coverage count (cancel bindings / goroutines / groups recognized) only reflects constructs the frontend actually modeled. A call to an unconfigured wrapper function (see `context_wrappers`/`start_wrappers`/`join_wrappers`/`stop_wrappers` above) never creates a binding to count in the first place, so it contributes nothing to this total and nothing to `unsupported_targets` either — there is no evidence trail for a construct the recognizer never matched syntactically. A nonzero coverage count in a function means *something* was checked; it does not mean *everything relevant* was checked.
- Aliasing is shallow. Storing a cancel/group value into an arbitrary container, or an ownership path more indirect than the three specific forms below, is still treated as an unverified ownership transfer, not followed further. As of this release, three forms of "passing" are verified rather than assumed instead of one:

  Passing a cancel/group value directly as an argument to a resolvable same-package function. `internal/frontend`'s `computeParameterEffects` (Phase 5, `docs/cfg-migration-plan.md`) determines what that function's own body does with the corresponding parameter, as an explicit set of effects (`model.ParamEffect`) rather than one "consumed" bit (audit finding F6): **may** (some reachable path calls it or waits on it), **must** (every path from entry to exit does, a `defer` covering every path that registered it), **returns** (handed back to the caller) and **opaque** (stored, sent, captured by a literal that may run, or passed somewhere not followed). The effect is applied at the call: a must effect is a cancel (or `Wait`) *at that call instruction*, so the owner's own all-path check judges it (`if c { always(cancel) }` is reported, `defer always(cancel)` is clean); a may-only effect is never a discharge, so `maybe(cancel, enabled)` with `if enabled { cancel() }` inside no longer erases the owner's obligation and is reported as called on some but not every path; returns and opaque stay a conservative hand-off, as before. Cleanup only counts if some normal path reaches it, so a call after an unconditional `return`, or inside a closure that never runs, establishes nothing. A recursion cycle is handled coinductively for the must question: a pass-through to a function in the same cycle counts as a discharge only in a function that has a real one of its own (`countdown(c, n-1)` that bottoms out in `c()`), while a cycle with no real discharge anywhere stays a leak. This is not a single declaration-order pass: `Build` runs it as a small interprocedural fixed point over a reverse call-dependency worklist. Every selected function is evaluated once initially; when a function's parameter summary grows, only its resolvable same-package callers are re-enqueued. Thus a chain of several hops (the callee passes the value on to a further function, which passes it on again) is verified to the same depth regardless of declaration order without repeatedly rescanning unrelated functions — confirmed concretely both ways for a 3-hop leak (`Start` -> `hop1` -> `hop2` -> `hop3`, where `hop3` drops the value) and for the same chain with `hop3` calling it instead, and for a cycle (mutual and self-recursion, where the fixed point still terminates and resolves to the correct answer rather than hanging or guessing). Three shapes that used to fall back unconditionally are now also verified, each in a narrow, purely syntactic (no control-flow, no points-to) way: a callee reached through a local variable or parameter assigned exactly once, anywhere in the function, to a bare named function (`var f func(context.CancelFunc) = drop; f(cancel)`) is resolved through that one assignment (`resolveCalleeFunc`) — two or more assignments anywhere, even along mutually exclusive branches, leaves it unresolved rather than guessing which one a given call reaches; a callee outside the current package is checked via a versioned fact (`Input.LookupParamEffects`, `analyzer.go`'s `FunctionFact.ParamEffects`), the same mechanism already used for a cross-package goroutine target, unavailable in standalone mode, and with exactly the semantics a same-package callee gets (a test exports a helper's effect and applies it through the lookup, and the result must equal the same helper in the same package); the older boolean hook `LookupParamConsumption` is still honored when no effect is available, reading "consumed" as an opaque hand-off and "not consumed" as a checked absence; and a `...` spread call is verified for the one shape Go's own semantics make meaningful — a slice of cancel-likes (directly, or through one single-assignment level of indirection: `all := []context.CancelFunc{cancel}; f(all...)`) spread into a `...context.CancelFunc`-shaped parameter, checked against the single recognized consuming idiom `for _, v := range cancels { v() }` (`variadicCancelElementCalled`) — a scalar spread has no meaningful position to resolve to at all, since `...` always fills the entire variadic slot with one slice value rather than distributing across parameters. When the callee still can't be resolved with confidence (an interface method, a function value written more than once, a slice built by `append` or returned from a call rather than a single literal assignment, or a parameter position that can't be mapped positionally), the check reports unverified and falls back to "assume transferred" the same way it always has — never the reverse; an inability to verify never manufactures a finding, and this fallback is unaffected by the fixed point or by any of the three narrower resolutions above.

  A verified group consumption specifically means the group is `Joined`, not `Escapes`, unlike the cancel case just above: a cancel binding has only one further-life question worth asking ("does something eventually call it"), for which `Escapes` is the right signal regardless of how consumption was verified, but a group has several more questions (`CountMismatch`'s literal Add/Done accounting chief among them) that engine.go skips over entirely whenever a group's `Escapes` is set, before ever consulting whether they independently already proved a real bug. `run(&wg)` where `run(g *sync.WaitGroup) { g.Wait() }` is a genuine, verified join — recording it as `Joined` keeps a real, already-computed `CountMismatch` finding live for a group started with `Add(2)` but only one spawned `Done()`, exactly as if `Wait()` had been called directly in the caller. `JoinedOnAllPaths` and `StopAfterWait` stay unestablished for a helper-mediated join regardless (the same as for a `join_wrapper` call): neither has a direct `Wait()` call site in the caller's own CFG to anchor to, which is a separate, pre-existing limitation this does not change. The callee's effect is judged on the callee's own structural control-flow graph, not on whether some call site's particular argument could reach a `Wait()`: `run(g *sync.WaitGroup, ok bool) { if ok { g.Wait() } }` called as `run(&wg, false)` is now reported, because the helper is may-only, but the literal `false` is never evaluated, so the same helper would be reported for a call that always passes `true`. A helper-mediated join is also now a join *site* in the owner's own graph, so `JoinedOnAllPaths` is established for it (`StopAfterWait` still reasons only about direct `Wait()` calls). A function literal's own control flow is not folded into the effect: a use inside a literal that may run is opaque, never must.

  **`Done()` effects.** The `wg.Add(1); go worker(&wg)` idiom asks a narrower question than the above: does the worker decrement the counter. `computeParamDoneEffects` answers it with the same may/must distinction (`Input.LookupParamDoneEffects`, `FunctionFact.ParamDoneEffects`), over reachable calls only, directly or through further same-package helpers. An observed `Done` somewhere is not presented as an all-path or exactly-once guarantee: a worker that calls `Done` only on some paths exports as may-only. The Add/Done tally still counts a may-only worker as one `Done`, because the only claim made from the tally is an undercount ("`Add(3)` but at most two `Done`s"), which holds even if every conditional `Done` fires, while an exact balance is never asserted. A `Done` inside a function literal is still not counted, and exactly-once is not checked (a worker that calls `Done` in a loop is not recognized as over-counting).

  Storing a cancel/group value into a named field of a *keyed* struct literal (`h := &Handle{cancel: cancel}`), tracked through two shapes ("field/constructor ownership tracking", `docs/roadmap.md` item 3): the literal assigned whole to a single named local variable ("stored struct"), and the same shape built directly inside a `return` statement, or via a local variable that is itself later returned unconsumed (a "constructor" returning the handle to its caller — the pattern this section used to call out as entirely unattempted). `internal/frontend`'s `collectFieldCaptures`/`resolveFieldCaptures` verify, for the "stored struct" form, whether that same local variable's own field is later called (a cancel function) or `Add`/`Go`/`Wait`-called (a group) anywhere else in the same function. For the "constructor" form, a further two-phase pre-pass — `computeFieldOwnership` then `computeConstructorCallerConsumption` — verifies the constructor's caller the same way. `computeFieldOwnership` runs once, over every function, before any caller-side check (the same "isolated pre-pass" reasoning `computeParameterConsumption` documents above). `computeConstructorCallerConsumption` used to be a single verified hop — this section used to say so explicitly, comparing itself to "Phase 5's own one-hop guarantee" from before that too became a fixed point — but is now a fixed point in its own right, solved with a reverse direct-call dependency worklist rather than whole-package sweeps: a caller that itself just returns the constructor's result onward, in either shape (`h, ctx := New(parent); return h, ctx`, or a bare `return New(parent)`, both recognized), is registered as a further, equally valid site for the same binding, and only callers of that newly recognized wrapper are revisited. A callee-indexed returned-field table avoids scanning every known binding for each call. Chains therefore resolve to any number of hops and regardless of declaration order without repeated global rescans. Each `returnFieldSite` carries its own resolved `kind` ("cancel", "waitgroup", or "errgroup") rather than having it re-derived from the binding's own object at every use: that re-derivation would silently fail once a chain passes through a cross-package origin (below), where the site's identity is necessarily a `*types.Func` substitute rather than a real cancel/group-typed variable, and a function's own signature is never itself cancel-like or group-like.

  Both of those shapes also verify a handle passed one step further, in either of two ways, rather than treating any such use as an automatic escape: a call to a same-package *method* on the handle (`h.Stop()`), or the handle passed as a direct *argument* to a resolvable same-package function (`register(h)`) — `followHandleMethod`/`followHandleArgument`, sharing one summary cache and cycle guard keyed by the specific local variable object being followed (`handleSummaryOf`), so a chain that mixes both shapes (a method forwarding its receiver to a helper function, which calls a further method on it) is followed uniformly, up to `maxReceiverDepth` (16) hops — a bound that exists only so a pathological or generated call graph cannot make one handle's verdict arbitrarily expensive, treated as unresolved (assume transferred) if hit, never as "not consumed". Whatever the callee's body calls or `Wait`s on the handle's behalf is credited back to the original call site, exactly like a direct `h.cancel()` would be; a callee that touches the field some other way, or does anything with the handle itself this narrow check does not follow (returns it, stores it, takes a method value without calling it, or reassigns its own copy of it), falls back to assume-transferred, the same conservative default as any other unresolvable use. Two shapes of callee are specifically *not* followed, both falling back the same way: a callee reached only through a `...` spread or variadic slice (no fixed single-argument position to resolve to), and a callee parameter with no name at all (`func(*Handle)`) — there is no identifier for this check to search the body for, unlike a *blank* `_` parameter name, which still names a real (if unreferenceable) parameter object and is followed like any other. A method promoted from an embedded field is not followed either, since its receiver is the embedded value, not the enclosing struct holding the tracked field.

  A tracked field that is later overwritten by a plain, direct assignment (`h.cancel = other`, as opposed to a new keyed literal) is not treated as a generic escape of the whole handle either: `captureFieldReassignment` closes off the old value's own "generation" as of that assignment (a later read through the field can no longer be mistaken for consuming it) and, when the new value is itself one of this build's own tracked bindings, opens a new generation for it starting there, verified completely independently of the one it replaced — including through a same-package method call or function argument, the same as any other generation. The old value, if it was never called before being overwritten, is a genuine, positive-evidence leak in its own right, not excused by whatever replaces it. This is bounded to a single function's own straight-line sequence of assignments, in source position order: it does not reason about which of two assignments in mutually exclusive `if`/`else` branches actually ran, so a field reassigned differently along two branches attributes a later read to whichever branch's assignment appears last in source, which is not necessarily the one that executed at runtime — a narrower form of the same non-path-sensitivity the "stored struct"/"constructor" checks above already have for a single conditional consuming call.

  A bare `x := w` (a whole-variable value copy) or `p := &w` (a pointer alias), where w already holds one of these captures, is not treated as a generic escape of w either (audit item #5, "alias/copy consume is fallback, not verification"): `collectFieldAliases` recognizes this exact shape and registers x/p as resolving to the same canonical capture w itself does, so a call through the alias is genuine, attributed consumption -- crediting the specific field actually called, not a blanket "w was used somehow" -- and, symmetrically, an alias that never calls the field back is now a real, reported leak rather than being silently masked by the copy/alias-creating assignment itself (which is treated as a documented no-op, the same as a tracked field's own direct reassignment is above). This is narrow and purely syntactic: only a bare identifier on both sides is recognized (a struct literal, a function call's own result, a field access, an index expression, or anything else on either side falls back to the ordinary default), chained aliases (`y := x` where x already aliases w) resolve through to w directly by construction (Go's declare-before-use rule guarantees x's own aliasing assignment is seen first in the same top-to-bottom scan), and this does not combine with field reassignment's own generation tracking above -- an alias created from one generation of a field does not specially track which generation it captured a snapshot of, though the ordinary position-based generation matching a read is checked against still applies to the alias's own occurrences the same as any other. Applies to both the same-function "stored struct" shape (`collectFieldAliases` scans the owner function's own body) and the constructor-caller shape (`verifyConstructorCallerField` scans each checked caller's own body the identical way).

  A `sync.WaitGroup` (or `errgroup.Group`) *value* field of a local struct variable (`var w struct{ a, b sync.WaitGroup }`) is tracked as its own independent group too (audit item #6, "in-struct WaitGroup fields never tracked"). Unlike every other binding in this file, such a field has no declaring identifier of its own anywhere in the source — it exists only as part of its struct's zero value — so `collectBindings`, which recognized a group only from its own declaring identifier, never saw it at all (`0 groups`, always clean). It now mints one synthetic `*types.Var` identity per owned field (`fieldGroupObject`, memoized per (owning variable, field name) pair: the struct's own field object is shared per *type*, so two variables of the same struct type must not collide), and `resolveGroupReceiver` correlates `w.a.Add(...)`/`w.a.Wait()` back to it. The rest of the pipeline sees an ordinary group. Because every other ownership-transfer mechanism here resolves an expression to a real `types.Object`, which a synthetic identity never is for something like `&w.a`, this is paired with a deliberately inverted safety net (`markFieldGroupEscapes`): for a synthetic group, *any* use of the owning variable other than a recognized direct `w.f.Add/Go/Wait/Done` call or an access to an unrelated field — passing or storing `w`, `&w` or `&w.f`, copying `w`, calling a method on `w` (whose body might touch the field), or reaching a field through embedding — is assumed to hand the group off and marks it escaped, never a finding. A blank discard (`_ = w`) is inert. Only *value*-typed group fields qualify: a *pointer*-typed field does not own its group and can alias one this function already tracks under its own real identity (`h := &Handle{wg: &wg}` makes `h.wg` and `wg` the same group), so claiming a second identity for it double-counted the group and reported the copy as never joined whenever the real one was — a false positive this capability's own first draft had, caught by probing before shipping. **Scope boundary, deliberately not hidden:** only `observeCall`'s own Starts/Joined accounting uses the extended receiver resolution, so a field group gets `LL1003` itself and the call-site-keyed ordering check (`JoinedOnAllPaths`, `StopAfterWait` — these key on the recorded call's own AST node, not on receiver resolution, so they apply for free), but *not* the later Phase 6 refinements that resolve a receiver through the plain `selectorReceiverObject` (`CountMismatch`, `UnjoinedRound`): a second round of work after the last `Wait()` on a field group is not caught the way it is for a plain local (`TestFieldGroup_SecondRoundReuseIsNotDetectedYet` pins this). Also out of scope: a struct that is a function *parameter* (its declaring identifier lives outside the body `collectBindings` walks), a group field reached through more than one selector (`w.inner.a`), and a struct variable whose own definition is not a local `var`/`:=`.

  This one no longer depends on a same-package `types.Object` to distinguish cancel from waitgroup/errgroup: `verifyConstructorCallerField` takes a plain `kind` string, derived either from the constructor's own binding object's static type (same-package, as before) or from a versioned fact (`model.Function.ReturnFieldSites`/`FunctionFact.ReturnFieldSites`, `Input.LookupReturnFieldSites`) describing, by result position, a returned field's name and kind — the exact same plain, object-free shape `ParamConsumption`/`ParamDoneCalled` already use. Consulted by `computeConstructorCallerConsumption` when a call's callee has no same-package `returnFieldInfo` entry. This fact is architecturally different from the other two, though, in a way worth being explicit about: `ParamConsumption`/`ParamDoneCalled` each answer a question purely about the *callee's own body* ("does this function consume its parameter"), true or false independent of who calls it or from where — exactly the shape a fact can answer once, on export, for every future importer. `ReturnFieldSites`' consumer-side check asks something different: whether the *caller* consumes a field of what it received — and for a same-package constructor, that verdict is recorded per call site (`b.callerVerdicts`) and reported *at the caller's own call*, because both functions are still being analyzed in the same `Build` call and the constructor's own binding is known there: that is how the analysis can tell whether anything is owed at all (a constructor that already cancels or joins on every path itself owes its callers nothing). A cross-package constructor's package has already been analyzed and its diagnostics already finalized by the time a dependent package is analyzed — facts flow from a dependency to its dependents, never backward — so there is no way for a caller-side finding to reach back and revise that already-reported verdict. For the same reason a caller of a cross-package constructor is not reported either: the fact carries the returned field's name and kind but not whether the constructor already discharges the obligation itself, so a finding there could be a false positive. Extending the fact to say so is what would lift this. What this extension does provide: `computeConstructorCallerConsumption` can now run at all for a cross-package callee (previously the same-package-`types.Object` dependency made it unreachable), and the verdict is recorded the same way a same-package one is (keyed by the callee's own `*types.Func`, there being no local binding object to key it by instead) — available to any future consumer that queries it directly, without a new diagnostic location invented for it here. Both forms are narrow and identity-tracked, not general alias analysis, exactly as `docs/cfg-migration-plan.md`'s Phase 3 scope note for this item requires (the one specific alias shape `collectFieldAliases` does recognize, described above, is a deliberately narrow, purely syntactic exception, not a step toward general alias analysis): only a keyed struct literal assigned to a single named local variable, or built directly in a return statement, is recognized at all — a positional (unkeyed) literal, a multi-name assignment, or the variable passed to a further function other than through one of the two recognized pass-through shapes above (as opposed to called, `Wait()`ed, blank-discarded with `_ =`, aliased via a bare `x := w`/`p := &w`, or returned) all still fall back to the prior plain, unverified "assume transferred" escape, exactly as before this capability existed. A read through an unrelated field of the same variable (e.g. printing a sibling `label` field) is correctly treated as harmless rather than as a disqualifying use.

  Storing a cancel value as an element of a slice or map literal (keyed or unkeyed; a map's own keys make no difference to its values), itself assigned exactly once to a single local variable ("container capture", the slice/map counterpart to the "stored struct" form above): `collectContainerCaptures` verifies whether that same variable is later ranged over and every element called, via the identical idiom `variadicCancelElementCalled` already uses for a `...`-spread variadic parameter above — `for _, v := range container { v() }`, no other shape recognized. A container also referenced anywhere else in the function beyond that one loop and its own declaration — passed to a further function, returned, or stored into another container (`containerHasOtherEscapingUse`) — is deliberately left unclaimed rather than guessed either way: its fate isn't decided within this one function, so the prior unverified "assume transferred" default applies, the same one-hop boundary every other direct verification in this file already stops at. A container built by `append`, returned from a call, or reassigned more than once is left unresolved by `singleAssignmentTargets` the same as anywhere else it's used. Group values are not covered by this form at all: `Wait()`/`Add()`/`Done()` is a multi-call protocol, not the single per-element call this idiom checks for, and a slice or map of group values has no equivalent single recognized consuming shape.

  "Aliasing is shallow" does not mean "any address-of/reassignment marks the original as transferred, full stop" — `internal/frontend`'s `resolveAliasEscapes` narrows that default specifically for the one case it can decide soundly: `other := &wg` / `other = &wg` (or, for a cancel, `other := cancel` / `other = cancel`) where `other` is *itself* a separately tracked cancel/group binding — any locally-declared variable of the matching type, since `groupKind` recognizes one regardless of whether it's ever passed anywhere; a cancel binding is narrower, tracked only when it comes directly from a recognized context-factory call, so this mostly matters when two such calls in the same function get cross-assigned. Recording the original as transferred the instant that assignment is observed, before anything is known about what happens to `other` afterward, previously discarded a real finding for no reason whenever `other` turned out to be entirely unused: `wg.Add(1); go worker; p := &wg` with no `Wait()` anywhere and `p` never subsequently referenced was reported clean, and the reported shape `p := &a; p = &b` with only `b` started and never waited was silent on `b` specifically because *reassigning* `p` a second time re-triggered the exact same unconditional rule for `b` too. `resolveAliasEscapes` runs once the whole function body has been walked and only marks the original as escaped if `other`'s own, independently-recorded final state shows some activity of its own (called/started, joined, or itself escaped) — an alias that is declared and never put to any use is not evidence that anything happened to the value it points to. When `other` *does* show activity, the original is still marked escaped, not credited with `other`'s own Joined/Called status directly: a later reassignment (as in the `p := &a; p = &b` shape above) can make an alias's eventual activity belong to a different original value by the time it happens, and disentangling that would mean tracking which value an alias points to at each point in the function — real alias analysis, not the identity-based tracking here. This is a narrowing of when the unverified-transfer default applies, not a new verified form of passing like the two above; it never turns a real transfer into a false "still owned here" positive, only stops crediting a transfer that never actually happened.

  A related, opposite-direction problem: `collectBindings` tracks every `*sync.WaitGroup`/`*errgroup.Group`-*typed* local variable as its own group, purely by type, regardless of whether it is a genuinely separate value or just a pointer alias for one already tracked elsewhere in the same function — necessarily so, since that is also the shape of an ordinary function *parameter* receiving a group by pointer, the common case this recognition exists for. A cancel binding has no equivalent risk: `collectBindings` only ever creates one by recognizing the specific `x, cancel := factory(...)` constructor-call shape, so every tracked cancel binding represents a genuinely separate construction event, never a bare alias. For groups specifically, this means a plain local pointer variable that is later pointed at an already-tracked `sync.WaitGroup` (`var p *sync.WaitGroup; p = &wg`) is not a second, independent group — it is the exact same underlying value, addressable and callable through either name — but is tracked as if it were one. `resolveAliasEscapes` therefore also marks such an alias's *own* binding as `Escapes`, unconditionally, once it is known to have been assigned the address of an already-tracked group at any point in the function: confirmed concretely, `var wg sync.WaitGroup; var p *sync.WaitGroup; p = &wg; p.Add(1); go func(){ wg.Done() }(); wg.Wait()` is entirely correct, safe code — `wg`'s counter genuinely goes 0 -> 1 -> 0 and `Wait()` genuinely unblocks — but previously produced a confirmed false positive: `LL1003` fired on `"p"` specifically, since `p.Add(1)` is attributed to `p`'s own independent binding while `wg.Done()`/`wg.Wait()` are attributed to `wg`'s own, separate binding (silent regardless, since `wg`'s own `Add` is never called directly), leaving `p` accounting for a start with no join ever observed through its own name. Unlike the original-side rule above, this one is unconditional rather than activity-gated, because this project treats a false positive as categorically worse than a false negative throughout: even a real, active use of the alias (`p.Add`/`p.Done`/`p.Wait` all called consistently, and genuinely balanced on their own) is left silent by this rule, since the alias's own accounting cannot be trusted to reflect calls meant for a single, consistent underlying value once it is known to have pointed somewhere else at some point — this analysis does not track which value an alias points to at each point in the function, by design. This costs coverage specifically on the alias's own name — a real bug reachable only through calls made via the alias, and never through the original's own name, is no longer caught — in exchange for never again reporting one that exists only because of this identity split. A diagnostic on the *original* binding's own name is completely unaffected and remains exactly as available as before. This rule is deliberately group-only: applying the equivalent unconditional suppression to a cancel binding was tried and reverted during development, because `cancel1 = cancel2` does not alias `cancel1` into `cancel2`'s already-tracked identity the way a pointer assignment does — it overwrites `cancel1`'s own variable, permanently losing whatever cancel function it held before (nothing else can reach that original value once the assignment runs), which is exactly the scenario the lost-cancel check exists to catch; suppressing `cancel1`'s own finding in that case would silently drop a real, independently confirmed bug (`TestCancelIdentity_ReassignedAliasDoesNotSuppressEitherCancel` pins this).

- `LL1002`'s verdict is computed from a real control-flow graph (`internal/cfg`), not from flat evidence booleans: an unconditional loop only fires when it forms a reachable, persistent (cyclic) strongly-connected component with no edge leaving it that can reach the function's exit. Each such component is judged independently, so a goroutine with two separate unconditional loops where only one has its own exit is correctly still flagged for the other — the case an earlier release's loop-scoped-but-still-per-goroutine evidence check could not close (`for { for { break } }`: the inner loop's exit no longer incorrectly clears the outer loop's finding). `tests/differential/cfg_ast_test.go` holds this as a fixed regression fixture. `break`, `continue`, and `goto` (including labeled forms) are resolved to their exact targets under Go's own grammar, not approximated; a `select` case's body is walked like any other block, so any termination mechanism within it (not only a literal `return` after `ctx.Done()`) is recognized structurally. A stop-wrapper call or a context passed to a called operation is represented as an extra trusted edge to exit, alongside the call's ordinary edge to the code after it (unlike a `return`, the call may return normally), since neither is otherwise visible in pure control flow; the assumed escape therefore only resolves a loop that *contains* the call — `ignore(ctx); for {}` is still flagged, where an earlier release modeled the call as a jump to exit and lost the loop entirely; `internal/cfg` itself has no notion of config or tracked contexts, only the predicate `internal/frontend` derives from them. This is still reachability over a graph, not a proof of termination: a resolving edge only says a recognized escape exists, not that every execution takes it, and a context passed to a called operation is trusted, not proved, to be honored by the callee.
- This CFG-based verdict applies directly whenever a body was available to build a CFG from. A cross-package goroutine target resolved through a `go vet` fact has no CFG of its own to build (only the exporting package had the body), but as of `FunctionFact.LoopUnresolved` (fact schema version 3), the exporting package computes this exact same CFG/SCC verdict for its own function and exports the result; the importing side trusts it the same way it trusts any other cross-package fact, rather than falling back to the older flat, whole-body evidence check. `tests/testdata/facts/mixed_consumer` and `tests/integration/integration_test.go`'s `TestVetCrossPackageFactCatchesMixedResolutionLoop` hold the exact mixed-resolution case as a regression fixture for this: it was a real false negative under the old fact format even after Phase 2 fixed the same-package/closure case, since a fact only carried flat booleans and the inner loop's break flattened into the whole function's `HasReturn`, wrongly clearing the outer loop's finding. A fact exported by an older binary (schema version below 3) does not carry `LoopUnresolved` and is simply unavailable to a newer one rather than reinterpreted — `ImportObjectFact` requires an exact version match.
- WaitGroup/errgroup verification (Phase 6, `docs/cfg-migration-plan.md`) goes beyond a flat "was Wait ever observed" boolean, but each of its checks is narrowly scoped and only ever fires from positive evidence. Count accounting (`sync.WaitGroup` only — `errgroup.Group` manages its own bookkeeping internally and has nothing analogous to get wrong) recognizes exactly two starting shapes: a literal (or constant-folded named `const`) `Add(n)`/`Done()` call outside any loop, and the common `Add(1)` paired with a worker that calls `Done()` on the same object — either an inline closure that does so directly, or a call to a resolvable function that receives the group as a direct argument and (verified by `computeParamDoneEffects`' own interprocedural fixed point, computed in the same reverse-dependency worklist as `computeParameterEffects`) eventually calls `Done()` on the corresponding parameter, to any number of hops of further same-package delegation (`wg.Add(1); go worker(&wg)` where `worker` calls `helper` which calls `Done()`, or a longer chain, resolved regardless of which order the functions are declared in) or, for a worker outside the current package, via a versioned fact (`Input.LookupParamDoneCalled`, `FunctionFact.ParamDoneCalled`) exactly analogous to `LookupParamConsumption` above — inside the same worklist, which balances itself regardless of delegation depth. Accounting is also path-sensitive: an `Add`/`Done` site inside one arm of an `if`/`switch`/`select` is isolated to that arm alone and only folds into the surrounding total when every one of that conditional's mutually exclusive arms nets to exactly zero on its own (the common `if needed { wg.Add(1); go worker() }` idiom, with no `else`, is exactly this case) — an `Add()` in one arm is never treated as balanced by an unrelated `Done()` in a sibling arm, since at runtime only one of them ever actually runs. Anything that doesn't fit one of these shapes — a non-literal amount, a loop-scoped call not part of the recognized pairing, several `Add(1)`s in a loop matched by only one spawned `Done`, a conditional whose arms don't all net to zero — leaves the count "not fully known" rather than guessing in either direction; a mismatch is only ever reported when every site for a group is accounted for and the literal totals still don't balance.

  Group identity is always per-object: a `Done()`, `Add()`, or `Wait()` call is attributed only to the specific `sync.WaitGroup`/`errgroup.Group` value it's actually called on, never to a different one merely because both are in scope or both are named similarly — a worker that mistakenly decrements the wrong group produces two independent, individually correct findings (the intended group's own outstanding worker, and the group it should have been calling `Wait()` on but wasn't) rather than either masking the other. A group reachable only through a struct field *that was never itself a recognized local `var`/`:=` group binding in the first place* is not tracked at all, consistent with the struct-field boundary above: field/constructor ownership tracking follows an *already-recognized* binding's identity through a field it is later stored into, it does not manufacture a new binding purely from a field's own declared type.

  Two ordering questions are deliberately left unverified rather than inferred from lexical position: whether a `Wait()` call precedes or follows a *later* `Add()` on the same group (an early, harmless `Wait()` on a still-zero counter is legal `sync.WaitGroup` usage and not flagged; reusing one `WaitGroup` for a second round of work is now checked, see below), and exactly what stop-before-wait's `LL1005` proves: only that a recognized stop-signal call is CFG-ordered before `Wait()`, never that the worker has actually observed and acted on that signal by the time `Wait()` unblocks — that would require reasoning about the concurrently-running goroutine's own execution, out of scope for a single-function CFG check.

  Reusing one `WaitGroup` for a second round of work with no matching second `Wait()` is now caught (`computeGroupRoundBalances`), where it previously wasn't: `Joined` alone is satisfied by the first `Wait()` call found anywhere in the function, and the whole-function `Add`/`Done` tally above sums across the entire function regardless of any `Wait()` calls in between, so `wg.Add(1); go worker(&wg); wg.Wait(); wg.Add(1); go worker(&wg); return` (a genuine bug — the second round is never waited on) was previously treated as perfectly fine by both checks: `Joined` is satisfied by the first `Wait()`, and the totals balance globally since the worker does call `Done()`. The fix splits the function's own top-level statement sequence into segments at each bare, top-level `Wait()` call and evaluates each segment against the specific thing that could go wrong for it: the segment after the group's *last* `Wait()` call has, by construction, no `Wait()` of its own following it, so any recognized worker-start there (`JoinGroup.UnjoinedRound`) is never joined — regardless of whether that round's own `Add`/`Done` happen to balance, since the bug is the missing synchronization point itself, not an imbalance in what's being synchronized (this is deliberately a separate field from `CountMismatch`, not a reuse of it, since the two questions are genuinely different and a shared boolean would blur which one actually failed). Every other segment *is* followed by a `Wait()` call, and that call blocks on the counter's cumulative value at the point it's reached, not that segment's own isolated contribution, so those segments are accumulated in execution order and checked after each one — catching, for instance, an intermediate `Wait()` reached while the counter is still nonzero even though a later, orphaned `Done()` call balances the whole-function total afterward, which the flat whole-function check alone would miss. Bounded to the function's own top-level, straight-line sequence: a bare, unconditionally-executed nested block or labeled statement is flattened into it (since those are just syntactic scope, always running in order regardless), but a loop or conditional's own body is left untouched and opaque, exactly as the whole-function check already treats it — a `Wait()` reached only through a branch, or only on some loop iterations, does not unconditionally close out a round the way a bare, top-level one does, and reasoning about that soundly would mean the interval/temporal analysis this stays narrow enough to avoid. A `defer Wait()` is deliberately never treated as a boundary either, for the same reason a deferred stop call isn't ordering-checked the way an inline one is: it runs at function exit, not inline at that point, so it cannot close out an earlier round the way a plain, sequential call does.

  A related, separate wrinkle: `internal/cfg` records a `defer` at the `defer` statement's own lexical position, not at the function's actual exit (where it really runs). For the common `defer wg.Wait()` placed immediately after declaring the `WaitGroup`, this puts the `Wait()` call site lexically before the `Add()`/`go` that follow it. The join check (`liveExitReachable`) therefore treats a deferred `Wait` as discharging every path that *registered* it, whether the registration comes before or after the worker start, rather than requiring it to follow the start the way a plain call must; that is exactly what `defer` means, and it is why the idiom is not flagged (`TestOrderingSemantics_DeferredWaitAtTopIsNotFlagged`). The converse is now checked too: a `defer` registered only after an early return does not cover the path that returned first (`TestAcquisition_Group`). The remaining imprecision is granularity: a deferred call inside a loop or a closure is credited as registered once its block is reached, and a `defer` inside a function literal is not part of this function's CFG at all.

  The same lexical-position wrinkle has a second, more consequential counterpart on the *stop* side of stop-before-wait, and this one is actively corrected rather than left as an accepted risk: `defer cancel()` placed immediately after `context.WithCancel`, with no other call to `cancel` anywhere in the function, genuinely deadlocks whenever a spawned worker blocks on that context's `Done()` before a `Wait()` call — the deferred `cancel()` cannot run until the function is already returning, which cannot happen until `Wait()` has returned, which cannot happen until the worker sees `Done()`, which cannot happen until `cancel()` runs. Left to `stopProvenAfterWait`'s ordinary same-block index comparison, the CFG's misleadingly early recorded position for this deferred call would make it look CFG-ordered *before* `Wait()` and never fire `LL1005` at all — the mirror-image mistake of the `defer wg.Wait()` case above, but on the side of missing a real, deterministic deadlock rather than merely missing a theoretical one. `computeStopOrdering` models this directly (audit finding F7): a deferred call runs when the function returns, after all plain code, and deferred calls run in the *reverse* of the order they were registered, with the registration order read off the CFG (which records a defer at its statement). So a deferred stop against a plain `Wait()` is after it; a plain stop against a deferred `Wait()` is before it; and with both deferred the one registered *later* runs first, so `defer wg.Wait(); defer cancel()` cancels first and is clean while `defer cancel(); defer wg.Wait()` waits first and is reported. Registration order that the graph cannot prove (a defer inside a branch, say) withholds the claim. The same applies to configured `stop_wrapper` calls, which `internal/cfg`'s defer mispositioning affects exactly as it does a cancel function. The old all-or-nothing test on the binding is gone: each stop signal is judged on its own, and a group is reported only when *every* one of its stop signals is proven to come after the `Wait()`, so an explicit `cancel()` ahead of `Wait()` alongside a `defer cancel()` safety net is clean (`examples/stop_before_wait`'s own shape), and so is a second `cancel()` after `Wait()`.

  Join-before-owner-return and stop-before-wait are both CFG reachability questions (`model.CFG.ReachableAvoiding`) rather than flat evidence, so a `Wait()` only reachable on some return paths, or a worker stop signal only reachable after `Wait()`, are now real findings the old flat booleans could not distinguish from "everything's fine" — and stop-before-wait relates each group to its own stop signals instead of pooling them per function (audit finding F7). A group's *workers* are the `go` statements that call `Done` on it (or pass it to a function that does), and the `Go` calls of a `WaitGroup`/`errgroup`. Its stop signals are the cancel functions of the contexts those workers use, directly or through contexts derived from them, plus any configured `stop_wrapper` call. A cancel function whose context no worker of the group uses is not its signal at all, so an unrelated goroutine's `defer cancel()` can no longer make a finite group look like it waited before its own signal, and two groups with two contexts are judged independently. A `stop_wrapper` names no context and no worker, so its connection to the group is an *assumption*: the finding says so (`stop_correlation: assumed-wrapper`, and the message reads "the wrapper is assumed to be what stops this group's workers"), where a context-correlated finding records `worker-context`. What is still not modeled: a worker that reaches its context some other way (a context stored in a struct field, fetched from a channel, or created inside a named function body) is not recognized as using it, so such a group gets no cancel-based stop signal and is not reported; stop mechanisms other than a cancel function or a configured wrapper (closing a channel, say) are not recognized; and a stop signal inside a function literal has no place in this function's graph, which withholds the claim. Both CFG checks are same-function only, same as everything else in this section not otherwise noted as cross-package.

  `LL1001`'s own `Called` was, until it was fixed, the one flat evidence boolean left in this whole area: a cancel func called under `if flag`, with no other call anywhere in the function, was indistinguishable from one called unconditionally, since "called anywhere" was Called's entire meaning — a real gap `JoinedOnAllPaths` had already closed for a WaitGroup's own `Wait()` call, just not yet for a cancel func's own call. `computeOrdering` now computes `CalledOnAllPaths` the identical way, for every cancel binding whose `Called` is already true: `ReachableAvoiding`, starting from the cancel function's creation rather than the function's entry (audit finding F3: a path that never created it owes no call), against the union of all of that binding's own recorded call sites, regardless of how each was credited (a direct call, one credited through a tracked struct field, or one credited through a same-package method call or function argument via `followHandleMethod`/`followHandleArgument` — all of them record the crediting call's own node in this function's own body, the only thing this check needs). A `defer cancel()` registered on every path from the creation to the exit covers them (`TestOrderingSemantics_DeferredCancelAtTopIsNotFlagged`), and one registered only after an early return does not cover the path that returned first. That is a true finding when the early return is unrelated to the factory: `ctx, cancel := context.WithCancel(p); if err := setup(); err != nil { return }; defer cancel()` leaks the context on the error path, and it fires (`TestCancelDeferAfterErrorCheckFiresLikeWaitGroupDoes`). The case that used to false-positive here, a configured context wrapper returning `(ctx, cancel, err)` followed by `if err != nil { return }; defer cancel()`, is now handled by an error guard (next paragraph); `examples/context_wrapper_typed_results` was adjusted before that existed, and no longer needs to be. A cancel function created *after* the early-return check owes nothing on the path that returned first, which was the common false positive here and is now fixed.

  **Error-returning factories (`errorBranchSkipper`).** When the factory call also assigns an error (a configured context wrapper returning `(ctx, cancel, err)`, or a constructor returning `(*Handle, error)` whose handle is returned in a field), the branch on which that error is non-nil is ruled out for the cleanup check: the factory is assumed to have created nothing there. So `ctx, cancel, err := Make(p); if err != nil { return err }; defer cancel()` is clean, while a *second*, unrelated early return after the check, a cancel only under an unrelated `if`, or a defer registered after such a return still warn. This rests on the factory's contract, which is **assumed, not verified**: a wrapper that returns a live `cancel` together with a non-nil error would leak on the path the guard excuses. When the guard is what changes a `LL1001` verdict for a cancel binding, the binding carries an `error-guard` evidence line saying so; the constructor-caller path has no evidence slot for it yet. A check only counts when it is one of the simple forms for which a branch implies a non-nil error: `err != nil` (then), `err == nil` (else), `!`, and `&&`/`||` combinations where the implication still holds for the whole condition (`err != nil && c` excuses its then branch, `err != nil || c` excuses nothing). It is deliberately conservative about whether the variable still holds the factory's result at the check: any other assignment to it between the call and the check disqualifies the check; a check inside a loop that does not contain the call is dropped if the loop assigns the variable; and a closure that assigns the variable, or taking its address, turns the guard off for that binding. Not modeled, so treated as an ordinary branch: `switch` on the error, `errors.Is` or helper predicates (`if !ok(err)`), a check on an alias of the error, `goto` back-edges, and a named-result error returned implicitly. Groups have no factory that reports an error, so the guard applies only to cancel bindings and constructor callers.

  The same question extends across a constructor/caller boundary (`docs/roadmap.md` item 3): a caller consuming the constructor's returned field only under `if flag`, with no other consuming caller, used to be verified identically to one consuming it unconditionally, since `verifyConstructorCallerField`'s own `consumed[fc]` was itself flat. `computeConstructorCallerConsumption` now builds one fresh, purely structural CFG per caller it checks (the caller's own, never the constructor's — the question is about the caller's control flow, not the constructor's) and asks the identical `ReachableAvoiding` question of that caller's own credited call sites. The verdict is kept per constructor call site (`b.callerVerdicts`), never merged across callers: each call creates a distinct runtime handle, so one caller consuming its own handle on every path says nothing about another caller that drops or only conditionally consumes its own. (An earlier release merged them with a "true wins permanently" rule, which let a single good caller silence every bad one and reported the leak at the constructor rather than at the caller that caused it — audit finding F2.) A call whose handle is passed somewhere this check does not follow, or forwarded onward by a pass-through wrapper, is unverified and yields no finding either way. A caller whose own consumption is partial is reported at its own call with `Called`/`CalledOnAllPaths` false (or `Joined`/`JoinedOnAllPaths` for a group) — the same engine.go message logic a same-function "stored struct" capture already uses applies unchanged. The constructor's own binding is settled as transferred (`Escapes`) as soon as any caller has been verified, and reports nothing itself. The caller-side finding has no suggested edit, since the caller has no cancel variable to `defer`; one binding returned through several results or fields is one obligation, discharged by consuming it through any of them.
- Configured wrappers use canonical names. A `start_wrapper`'s entry point is found among its arguments by type: an inline closure or a reference to a top-level declared function are both recognized, in either argument position, with no separate config needed to say where the callback is. A `context_wrapper`'s context and cancel-function results are identified by their static types rather than by position, so a wrapper may return them in either order and may return additional results (e.g. a trailing `error`) alongside them. `join_wrapper`/`stop_wrapper` matching was already independent of argument position. What remains unconfigurable: a function-typed value stored in a variable, struct field, or returned from another call (as opposed to a literal closure or a direct reference to a declaration) is not resolved, for either a `go` statement or a configured start wrapper — this is the same conservative boundary `buildGoroutine` already applies to plain `go` statements, not a gap specific to configuration.
- Function literals are analysis units of their own. A cancel function or join group declared inside a literal is judged exactly like one declared in a named function, and a finding is attributed to the literal's identity (`outer.func1`, `outer.func1.1`, following the toolchain's closure naming) at the right line; literals count against `max_functions` after every named function, so a truncated run drops closures first. What stays approximate:
  - A literal owns only what it declares. A cancel function or group declared outside and merely assigned or started inside it is judged by the enclosing function, where all its uses are visible.
  - Defining a closure is not invoking it, but only the clearest never-run shapes are recognized: a literal assigned to `_` (or `var _`), or held by a local variable whose every use is a blank assignment. What such a literal's body does, such as calling a captured cancel function, discharges nothing. Every other literal is treated as invoked or transferred and keeps being credited as before.
  - A captured outer cancel function or group used inside an *invoked or transferred* literal still counts permissively, and the all-path check for it stays unestablished, because the literal's own control flow is not folded into the enclosing function's: `func() { if c { cancel() } }()` is not reported. Closure definition, invocation and escape are not yet separate events there; stored-then-called (`f := func(){...}; f()`) and callback shapes are not mapped to their call sites.
  - Package-level function literals (a `var handler = func() {...}`) are not analyzed, because they belong to no declaration.
  - A literal unit reports only cancel and group findings. Goroutine findings and the lifecycle summary stay with the enclosing declaration, which already walks into the literal, so nothing is reported twice.
- Standalone `-tests` includes same-package test files but not external `package_name_test` packages. Vet mode receives normal Go compilation units.
- Suggested edits are emitted only for a blank cancel result in a short declaration, and only where the rewrite is valid Go that keeps the resource's scope and lifetime (see the README's "Safe suggested fix"). It is withheld for `if`/`for`/`switch` initializers, anywhere inside a `for` or `range` body, under a label or in a function that uses `goto`, and when the cancel function takes an argument. Those cases keep their diagnostic and need a manual fix: rewriting an initializer or releasing per iteration is a different, scope-preserving transformation that is not attempted. The checks are structural and conservative: a `goto` anywhere in the function withholds every fix in it, and a function literal's own statements are not analyzed (so get no fix). A fix inside a plain nested block is still offered, and its `defer` runs at function return like any `defer cancel()` written there by hand.
- The local SSA-like summary has no phi nodes and is not a full control-flow SSA representation.

## Run status and what "complete" means

`status.incomplete` (and the JSON `incomplete` flag) says a bound or a deadline stopped the run, nothing more. It is deliberately not "semantically complete": a run with `incomplete: false` has analyzed everything it was given, under the model's approximations, and has not proven that no violation exists. What the model approximated is counted separately in `status.unsupported`:

- `targets`: goroutine start sites whose body could not be inspected;
- `handed_off_obligations`: cancel functions and join groups assumed to have moved elsewhere (stored in a field or global, returned, sent, captured by a function literal that may run, or passed somewhere not followed) and not judged further in the function that created them. A constructor whose callers in the package are checked at their own call sites is not counted, because that transfer is verified; a cancel function returned to a caller outside that tracking is;
- `unestablished_path_checks`: bindings known to be discharged somewhere whose all-paths question has no answer, so they are credited, not verified (for example a discharge inside a closure that may run).

Things this status does **not** count, so a zero is not evidence of their absence: wrapper functions not declared in the configuration (they create no binding at all), unmodeled calls that never touched a tracked value, aliasing the model does not follow, function literals at package level, and the effects of reflection or generated dispatch. `excluded_files` counts files removed by `ignore_paths` or because they are generated, which were never analyzed. The status is function- and package-scoped like the analysis: under `go vet` it is per package (`-lifeline.status-out` writes one record each, and `go vet` also analyzes dependencies for facts, so the file contains a record for every package vet visited, not only the ones named on the command line).

A timeout in standalone mode is recorded in the status, and its `LL9001` notice follows `ignore` like every other diagnostic. `fail_on_incomplete` and `fail_on_unsupported` read only the status. The deadline is now propagated into frontend fixed points, receiver-owned AST walks, CFG construction, and local SSA-like construction; `go vet` applies the same timeout per package. Cancellation can therefore interrupt a large frontend analysis instead of being noticed only between packages. This is still cooperative rather than a hard process deadline: `parser.ParseFile` and `go/types.Config.Check` are synchronous/non-cooperative, and a few bounded helper scans observe cancellation only when they return. A very large parse or type-check can therefore overrun the configured timeout before the next checkpoint.

## False positives and negatives

A warning means the supported model found a missing protocol element. Code may still terminate through an unsupported mechanism. Conversely, accepting a context argument, break, return, or channel-close path is not proof that the path is reachable or correctly owned.

Prefer Lifeline as review evidence rather than an unsupervised correctness gate. CI failure is opt-in for this reason.

## Generated files and suppression

A file carrying the standard `// Code generated ... DO NOT EDIT.` marker (https://go.dev/s/generatedcode) is automatically excluded from analysis in both standalone and vet mode; it contributes no diagnostics and no coverage counts, as if it were not part of the package. A file can also be excluded by path via the `ignore_paths` config list, matched with `filepath.Match` semantics (no `**`; write a pattern like `*.pb.go` to match at any depth by basename rather than a directory-spanning pattern) against both the file's path relative to the working directory and its base filename.

A specific finding can be suppressed inline with a `//lifeline:ignore` comment. `//lifeline:ignore` alone suppresses every rule reported on that line; `//lifeline:ignore LL1001,LL1002` suppresses only the listed rules, and free text may follow (e.g. `//lifeline:ignore LL1002 -- see TICKET-123`). The comment is matched against the diagnostic's own reported line and against every evidence span's line, so it can go on whichever line most naturally names the construct — for `LL1002` in particular, that is usually the loop itself (e.g. `for { //lifeline:ignore`), which is a different line than the diagnostic's own reported position at the goroutine's start site. As before, rule-level `ignore` in config or restricting package patterns remain the coarser-grained options.

## Resource and timing limits

Standalone root packages are analyzed concurrently. Package loading checks cancellation between source files and before/after type checking; frontend fixed points and the main AST/CFG/local-IR traversals poll the deadline while they run. Vet uses the configured timeout as a per-package frontend deadline. Parsing one source file and Go type checking remain synchronous library calls, so cancellation during either is observed only after that call returns.

There is still no node/edge/update or memory budget, and no process isolation for non-cooperative compiler operations. The timeout is therefore a cooperative resource control, not an exact wall-clock guarantee. End-to-end runtime is recorded in the evaluation document; phase-separated parse/type-check/model/recognition/render timing is not yet emitted by the tool.
