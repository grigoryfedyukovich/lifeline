# Limitations

Lifeline 0.1.1 is intentionally conservative and bounded.

## Unsupported or approximate cases

- Indirect calls through interfaces, reflection, arbitrary function values, and generated dispatch are not resolved.
- Same-package direct goroutine targets are inspected only when they are within `max_functions`.
- Vet mode may use a compatible direct-function fact for a cross-package target. Standalone mode does not import those facts. As of this release this asymmetry is disclosed rather than silent: a standalone run that hits a cross-package target reports it under "goroutine target(s) could not be analyzed" in the clean-result summary (text) or `coverage.unsupported_targets` (JSON/SARIF), instead of indistinguishably reporting "no lifecycle diagnostics."
- Unsupported target bodies are retained as model evidence and are now surfaced in the report as coverage information (text: listed under a clean result; JSON/SARIF: `coverage.unsupported_targets`). They are informational, not diagnostics: they carry no rule ID, cannot match `-fail-on`, and are excluded from the pass/fail decision — a goroutine whose body could not be inspected is neither a finding nor proof of correctness.
- The coverage count (cancel bindings / goroutines / groups recognized) only reflects constructs the frontend actually modeled. A call to an unconfigured wrapper function (see `context_wrappers`/`start_wrappers`/`join_wrappers`/`stop_wrappers` above) never creates a binding to count in the first place, so it contributes nothing to this total and nothing to `unsupported_targets` either — there is no evidence trail for a construct the recognizer never matched syntactically. A nonzero coverage count in a function means *something* was checked; it does not mean *everything relevant* was checked.
- Aliasing is shallow. Storing a cancel/group value into an arbitrary container, or an ownership path more indirect than the two specific forms below, is still treated as an unverified ownership transfer, not followed further. As of this release, two forms of "passing" are verified rather than assumed instead of one:

  Passing a cancel/group value directly as an argument to a resolvable same-package function. `internal/frontend`'s `computeParameterConsumption` pre-pass (Phase 5, `docs/cfg-migration-plan.md`) determines whether that function's own body actually consumes the corresponding parameter (calls it, or itself further transfers it via any already-recognized escape form). The direct, one-hop case — the immediate callee's own body — is verified reliably regardless of source order: the pre-pass computes every function's result before any caller's check runs. A chain of several hops (the callee passes the value on to a further function, which passes it on again) can also be verified, but only as far as the pre-pass happens to have already computed a deeper callee's result by the time an earlier one needs it — which depends on declaration order (a plain single pass over functions in source order, not a call-graph-aware one), not something this release guarantees for chains beyond the first hop. Confirmed concretely: a 3-hop leak (`Start` -> `hop1` -> `hop2` -> `hop3`, where `hop3` drops the value) is caught when the functions happen to be declared leaf-first, and missed — falling back safely to the prior "assume transferred" behavior, not a false positive — when declared caller-first, the more common style. Ordering the pre-pass by the call graph rather than declaration order would make multi-hop chains reliable regardless of source order; that is a bounded, well-defined follow-up (`docs/roadmap.md`), not attempted here. When the callee can't be resolved at all with confidence (a different package, an interface method, a function value, a `...` spread call, or a parameter position that can't be mapped positionally), the check reports unverified and falls back the same way — never the reverse; an inability to verify never manufactures a finding.

  Storing a cancel/group value into a named field of a *keyed* struct literal (`h := &Handle{cancel: cancel}`), tracked through two shapes ("field/constructor ownership tracking", `docs/roadmap.md` item 3): the literal assigned whole to a single named local variable ("stored struct"), and the same shape built directly inside a `return` statement, or via a local variable that is itself later returned unconsumed (a "constructor" returning the handle to its caller — the pattern this section used to call out as entirely unattempted). `internal/frontend`'s `collectFieldCaptures`/`resolveFieldCaptures` verify, for the "stored struct" form, whether that same local variable's own field is later called (a cancel function) or `Add`/`Go`/`Wait`-called (a group) anywhere else in the same function. For the "constructor" form, a further two-phase pre-pass — `computeFieldOwnership` then `computeConstructorCallerConsumption`, mirroring `computeParameterConsumption`'s own reasons for running in isolation from `buildFunction`'s main loop — verifies the constructor's direct, resolvable, same-package caller the same way, one hop only, and (unlike the parameter-passing chain above) does so regardless of which of the two functions is declared first, since both pre-pass phases run to completion over every function before the next begins. A caller that itself just forwards the handle to a further function is not chased into: the same one-hop boundary already described for direct argument passing. Both forms are narrow and identity-tracked, not general alias analysis, exactly as `docs/cfg-migration-plan.md`'s Phase 3 scope note for this item requires: only a keyed struct literal assigned to a single named local variable, or built directly in a return statement, is recognized at all — a positional (unkeyed) literal, a multi-name assignment, a slice/map/array container, or the variable passed on to any further function (as opposed to called, `Wait()`ed, blank-discarded with `_ =`, or returned) all still fall back to the prior plain, unverified "assume transferred" escape, exactly as before this capability existed. A read through an unrelated field of the same variable (e.g. printing a sibling `label` field) is correctly treated as harmless rather than as a disqualifying use.
- `LL1002`'s verdict is computed from a real control-flow graph (`internal/cfg`), not from flat evidence booleans: an unconditional loop only fires when it forms a reachable, persistent (cyclic) strongly-connected component with no edge leaving it that can reach the function's exit. Each such component is judged independently, so a goroutine with two separate unconditional loops where only one has its own exit is correctly still flagged for the other — the case an earlier release's loop-scoped-but-still-per-goroutine evidence check could not close (`for { for { break } }`: the inner loop's exit no longer incorrectly clears the outer loop's finding). `tests/differential/cfg_ast_test.go` holds this as a fixed regression fixture. `break`, `continue`, and `goto` (including labeled forms) are resolved to their exact targets under Go's own grammar, not approximated; a `select` case's body is walked like any other block, so any termination mechanism within it (not only a literal `return` after `ctx.Done()`) is recognized structurally. A stop-wrapper call or a context passed to a called operation is represented as a trusted edge straight to exit (the same way a `return` is), since neither is otherwise visible in pure control flow; `internal/cfg` itself has no notion of config or tracked contexts, only the predicate `internal/frontend` derives from them. This is still reachability over a graph, not a proof of termination: a resolving edge only says a recognized escape exists, not that every execution takes it, and a context passed to a called operation is trusted, not proved, to be honored by the callee.
- This CFG-based verdict applies directly whenever a body was available to build a CFG from. A cross-package goroutine target resolved through a `go vet` fact has no CFG of its own to build (only the exporting package had the body), but as of `FunctionFact.LoopUnresolved` (fact schema version 3), the exporting package computes this exact same CFG/SCC verdict for its own function and exports the result; the importing side trusts it the same way it trusts any other cross-package fact, rather than falling back to the older flat, whole-body evidence check. `tests/testdata/facts/mixed_consumer` and `tests/integration/integration_test.go`'s `TestVetCrossPackageFactCatchesMixedResolutionLoop` hold the exact mixed-resolution case as a regression fixture for this: it was a real false negative under the old fact format even after Phase 2 fixed the same-package/closure case, since a fact only carried flat booleans and the inner loop's break flattened into the whole function's `HasReturn`, wrongly clearing the outer loop's finding. A fact exported by an older binary (schema version below 3) does not carry `LoopUnresolved` and is simply unavailable to a newer one rather than reinterpreted — `ImportObjectFact` requires an exact version match.
- WaitGroup/errgroup verification (Phase 6, `docs/cfg-migration-plan.md`) goes beyond a flat "was Wait ever observed" boolean, but each of its checks is narrowly scoped and only ever fires from positive evidence. Count accounting (`sync.WaitGroup` only — `errgroup.Group` manages its own bookkeeping internally and has nothing analogous to get wrong) recognizes exactly two starting shapes: a literal (or constant-folded named `const`) `Add(n)`/`Done()` call outside any loop, and the common `Add(1)` paired with a worker that calls `Done()` on the same object — either an inline closure that does so directly, or a call to a resolvable same-package function that receives the group as a direct argument and calls `Done()` on the corresponding parameter (a named-function worker, e.g. `wg.Add(1); go worker(&wg)`, is recognized the same way an inline closure is, one hop only: if `worker` itself delegates to a further helper that calls `Done()`, that is not attempted) — inside the same loop, which balances itself regardless of iteration count. Accounting is also path-sensitive: an `Add`/`Done` site inside one arm of an `if`/`switch`/`select` is isolated to that arm alone and only folds into the surrounding total when every one of that conditional's mutually exclusive arms nets to exactly zero on its own (the common `if needed { wg.Add(1); go worker() }` idiom, with no `else`, is exactly this case) — an `Add()` in one arm is never treated as balanced by an unrelated `Done()` in a sibling arm, since at runtime only one of them ever actually runs. Anything that doesn't fit one of these shapes — a non-literal amount, a loop-scoped call not part of the recognized pairing, several `Add(1)`s in a loop matched by only one spawned `Done`, a conditional whose arms don't all net to zero — leaves the count "not fully known" rather than guessing in either direction; a mismatch is only ever reported when every site for a group is accounted for and the literal totals still don't balance.

  Group identity is always per-object: a `Done()`, `Add()`, or `Wait()` call is attributed only to the specific `sync.WaitGroup`/`errgroup.Group` value it's actually called on, never to a different one merely because both are in scope or both are named similarly — a worker that mistakenly decrements the wrong group produces two independent, individually correct findings (the intended group's own outstanding worker, and the group it should have been calling `Wait()` on but wasn't) rather than either masking the other. A group reachable only through a struct field *that was never itself a recognized local `var`/`:=` group binding in the first place* is not tracked at all, consistent with the struct-field boundary above: field/constructor ownership tracking follows an *already-recognized* binding's identity through a field it is later stored into, it does not manufacture a new binding purely from a field's own declared type.

  Two ordering questions are deliberately left unverified rather than inferred from lexical position: whether a `Wait()` call precedes or follows a *later* `Add()` on the same group (an early, harmless `Wait()` on a still-zero counter is legal `sync.WaitGroup` usage and not flagged; conversely, reusing one `WaitGroup` for a second round of work with no matching second `Wait()` is not currently caught either — `Joined` is satisfied by the first `Wait()` call found anywhere in the function, and per-round temporal tracking is a materially larger undertaking than the reachability and literal-sum checks here), and exactly what stop-before-wait's `LL1005` proves: only that a recognized stop-signal call is CFG-ordered before `Wait()`, never that the worker has actually observed and acted on that signal by the time `Wait()` unblocks — that would require reasoning about the concurrently-running goroutine's own execution, out of scope for a single-function CFG check.

  Join-before-owner-return and stop-before-wait are both CFG reachability questions (`model.CFG.ReachableAvoiding`) rather than flat evidence, so a `Wait()` only reachable on some return paths, or a worker stop signal only reachable after `Wait()`, are now real findings the old flat booleans could not distinguish from "everything's fine" — but stop-before-wait's notion of "the worker's stop signal" is a function-scoped heuristic (any configured `stop_wrapper` call, or any tracked context's cancel function that is both called and captured by some goroutine started in the same function), not correlated to which specific group a given goroutine belongs to; a function juggling more than one WaitGroup/errgroup and more than one stop mechanism could have a stop signal credited to the wrong group's check. Both CFG checks are same-function only, same as everything else in this section not otherwise noted as cross-package.
- Configured wrappers use canonical names. A `start_wrapper`'s entry point is found among its arguments by type: an inline closure or a reference to a top-level declared function are both recognized, in either argument position, with no separate config needed to say where the callback is. A `context_wrapper`'s context and cancel-function results are identified by their static types rather than by position, so a wrapper may return them in either order and may return additional results (e.g. a trailing `error`) alongside them. `join_wrapper`/`stop_wrapper` matching was already independent of argument position. What remains unconfigurable: a function-typed value stored in a variable, struct field, or returned from another call (as opposed to a literal closure or a direct reference to a declaration) is not resolved, for either a `go` statement or a configured start wrapper — this is the same conservative boundary `buildGoroutine` already applies to plain `go` statements, not a gap specific to configuration.
- Cancellation bindings created inside anonymous functions are not promoted to separate top-level function records, although uses of enclosing bindings and nested goroutine starts are observed.
- Standalone `-tests` includes same-package test files but not external `package_name_test` packages. Vet mode receives normal Go compilation units.
- Suggested edits are emitted only for a blank cancel result in a short declaration.
- The local SSA-like summary has no phi nodes and is not a full control-flow SSA representation.

## False positives and negatives

A warning means the supported model found a missing protocol element. Code may still terminate through an unsupported mechanism. Conversely, accepting a context argument, break, return, or channel-close path is not proof that the path is reachable or correctly owned.

Prefer Lifeline as review evidence rather than an unsupervised correctness gate. CI failure is opt-in for this reason.

## Generated files and suppression

A file carrying the standard `// Code generated ... DO NOT EDIT.` marker (https://go.dev/s/generatedcode) is automatically excluded from analysis in both standalone and vet mode; it contributes no diagnostics and no coverage counts, as if it were not part of the package. A file can also be excluded by path via the `ignore_paths` config list, matched with `filepath.Match` semantics (no `**`; write a pattern like `*.pb.go` to match at any depth by basename rather than a directory-spanning pattern) against both the file's path relative to the working directory and its base filename.

A specific finding can be suppressed inline with a `//lifeline:ignore` comment. `//lifeline:ignore` alone suppresses every rule reported on that line; `//lifeline:ignore LL1001,LL1002` suppresses only the listed rules, and free text may follow (e.g. `//lifeline:ignore LL1002 -- see TICKET-123`). The comment is matched against the diagnostic's own reported line and against every evidence span's line, so it can go on whichever line most naturally names the construct — for `LL1002` in particular, that is usually the loop itself (e.g. `for { //lifeline:ignore`), which is a different line than the diagnostic's own reported position at the goroutine's start site. As before, rule-level `ignore` in config or restricting package patterns remain the coarser-grained options.

## Resource and timing limits

Standalone root packages are analyzed concurrently, but parsing and type checking inside one package are synchronous. A deadline that expires during one of those phases is observed when the operation returns or the next cancellation boundary is reached.

End-to-end runtime is recorded in the evaluation document. Phase-separated parse/type-check/model/recognition/render timing is not yet emitted by the tool.
