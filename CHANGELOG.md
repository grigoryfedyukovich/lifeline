- **Phase 5 parameter-passing ownership verification:** `internal/frontend.computeParameterConsumption` pre-pass and `argumentConsumed` verify direct cancel/group arguments passed to resolvable same-package callees. The implementation is intentionally a single source-order pre-pass: one-hop verification is order-independent, while deeper multi-hop verification may depend on declaration order. `internal/frontend/frontend_test.go` covers the supported direct cases and explicitly tests both sides of the known 3-hop declaration-order limitation; unverified calls retain the conservative assume-transferred behavior.

- Fixed a Phase 6 `LL1005` (stop-before-wait) false negative: `defer cancel()` placed immediately after `context.WithCancel`, with no other call to `cancel` anywhere in the function, genuinely deadlocks a `Wait()`-blocked worker waiting on that context's `Done()` — but `internal/cfg` records a `defer` at its own lexical position rather than at the function's actual exit, so `stopProvenAfterWait`'s ordinary same-block index comparison saw the deferred call as CFG-ordered *before* `Wait()` and never fired. `internal/frontend.computeGroupOrdering` now special-cases a cancel binding via two new helpers, `deferredCallSet` and `allCallsDeferred`: when *every* recorded call site for a qualifying cancel binding is a deferred call, the binding is treated as unconditionally stop-after-wait, bypassing the misleading position entirely. - **Field/constructor ownership tracking** (`docs/roadmap.md` item 3): a cancel/group binding stored into a named field of a *keyed* struct literal is now verified against that specific field's later use instead of being unconditionally treated as an already-discharged ownership transfer the instant it is stored -- the gap this section's own limitations paragraph used to call out as entirely unattempted. Two shapes are recognized, both in `internal/frontend/frontend.go`:
  - **Stored struct**: the literal assigned whole to a single named local variable (`h := &Handle{cancel: cancel}`). A new pre-collection pass, `collectFieldCaptures`, recognizes this shape (a keyed struct composite literal, directly or via `&`, as the sole right-hand side of a single-name `:=`/`=`/`var` binding) instead of letting the existing generic `observeContainerEscape` treat it as an unconditional escape; `resolveFieldCaptures` then searches the rest of the function body once (`walkFieldCaptureUses`) for a verified consuming use through that same variable's field -- a call through the field for a cancel function, or an `Add`/`Go`/`Wait` call through the field for a group, mirroring the same three methods `observeCall`'s direct-receiver handling already recognizes. A variable confidently local, never consumed, and never used any other way is left exactly as constructed (`Called`/`Joined`/`Escapes` all false), so the ordinary `LL1001`/`LL1003` checks fire on this positive evidence -- the "stored struct" leak this capability exists to catch. A read through an *unrelated* field of the same variable (e.g. a sibling `label` field) is correctly classified as harmless rather than as a disqualifying use, and so is the common `_ = h` discard idiom; passing the variable to any further function, reassigning it, or any other more indirect use falls back to the prior conservative assume-transferred default, the same as before this capability existed.
  - **Constructor-returned objects**: the same shape built directly inline in a `return` statement, or via a local variable that is itself later returned unconsumed -- a function whose whole job is to construct and hand back a handle. Two further pre-passes, run the same way `computeParameterConsumption` (Phase 5) already runs as an isolated pass over every function before `buildFunction`'s main loop: `computeFieldOwnership` finds every function returning a binding this way (`b.returnFieldInfo`), then `computeConstructorCallerConsumption` checks every other function as a potential direct caller, reusing the exact same `walkFieldCaptureUses` machinery against the *caller's* body to determine whether the returned struct's field is read back and consumed there. This is a single verified hop, the same guarantee Phase 5's own `argumentConsumed` gives for direct parameter passing: an unresolved or further-indirect caller (the handle forwarded to yet another function, an interface method, a different package) leaves the binding unverified, which falls back to "assume transferred" exactly like every other unverified case in this file -- never a false positive. Unlike Phase 5's own single-pass parameter-consumption check, this is verified regardless of which of the two functions -- constructor or caller -- is declared first in source order, since both new pre-passes run to completion over every function before the next phase begins.
  - Deliberately not general heap/alias analysis, per `docs/cfg-migration-plan.md`'s Phase 3 scope note for this item: only a *keyed* struct literal assigned to a single named local variable, or built directly in a `return`, is ever recognized. A positional (unkeyed) literal, a multi-name assignment, a slice/map/array composite literal, and a value passed on to any further function all still fall back to the prior plain, unverified escape untouched -- confirmed by dedicated fallback-boundary tests, not just the positive cases.

No existing diagnostic verdict changed: every case not matching one of the two new narrow shapes falls back to exactly the prior behavior, and Phase 4-6 and Phase 5's own single-pass parameter-consumption mechanism are untouched.

- Fixed two Phase 6 WaitGroup accounting bugs found by an external benchmark run (`phase6-fix-requirements.md`), both in `internal/frontend/frontend.go`'s count-balance check:
  - A named-function goroutine target's own `Done()` call (`wg.Add(1); go worker(&wg)`, where `worker` calls `wg.Done()` on its own parameter) was invisible to `walkGroupBalance`, which only recognized an inline closure (`go func(){ defer wg.Done() }()`) doing the same thing. This was a false positive: the extremely common named-worker idiom was reported as an outstanding worker even when correctly balanced. Fixed by a new `calleeDoneParamMatches`, a one-hop existence check (resolve the callee, find which parameter position receives the group, check whether that function's body calls `Done()` on it) -- deliberately not a reuse of Phase 5's `paramConsumption` fixed point, which answers a different question (does the parameter get `Wait()`ed or further transferred) appropriate for verifying an ownership handoff, not for a worker whose whole job is to decrement the counter its caller already incremented.
  - Count-balance accounting was not path-sensitive at all: every `Add`/`Done` site found anywhere in a function body was summed into one shared running total regardless of which conditional branch it was in, so an `Add()` in one arm of an `if`/`switch`/`select` and an unrelated `Done()` in a sibling arm -- which can never actually execute together, since exactly one arm runs -- could be treated as balancing each other. This could mask a real per-branch imbalance, or, in principle, fabricate a mismatch that no single execution of the function ever actually produces. Fixed by restructuring `walkGroupBalance` around isolated per-arm accounting: each arm of a conditional is walked into its own fresh, self-contained `groupBalance` (`walkGroupBalanceStmts`), and the arms are only folded into the enclosing total when *every* arm's own net delta (`addTotal - doneTotal`) is exactly zero and every arm is itself fully known (`foldConditionalArms`) -- the common conditionally-started-worker idiom (`if needed { wg.Add(1); go worker() }`, no `else`) is exactly this safe case, since that one arm's own Add/spawned-Done pair already nets to zero and the implicit empty `else` is trivially zero too. An arm with a nonzero delta, or an `else`-less `if` whose one arm doesn't net to zero, now correctly leaves the whole group "not fully known" (silent) rather than either falsely balanced or falsely flagged. `ForStmt`/`RangeStmt` loop-scoped accounting (the pre-existing `addOnes`/`spawnedDones` idiom-matching) is unchanged and still folds directly into the enclosing scope regardless of nesting depth, matching its prior behavior exactly.

Four upgrades, each firing only from positive structural or CFG evidence, never from an inability to verify:
  - **Count intervals & common Add/Done relationships** (`internal/frontend.computeGroupBalances`, `sync.WaitGroup` only): a dedicated second pass over the function body sums literal `Add(n)`/`Done()` call sites outside any loop (via `go/constant`'s own constant folding, so a named `const` counts the same as a bare literal), and separately recognizes the common `Add(1)` immediately paired with a `go func(){ defer wg.Done() }()` inside the same loop as self-balancing regardless of how many times that loop actually runs (`loopScope` accounting, closed and reconciled once each loop's own body has been fully walked). `JoinGroup.CountMismatch` is set only when every Add/Done site for a group fits one of those two shapes and the literal totals still don't balance; anything else (a non-literal amount, an unmatched loop-scoped call) leaves the count "not fully known" rather than guessing. `errgroup.Group` is exempt: its own bookkeeping is internal to the library.
  - **Join-before-owner-return** (`internal/frontend.computeGroupOrdering`): a new `model.CFG.ReachableAvoiding(start, avoid)` primitive (reachability from `start` treating every block in `avoid` as deleted) checks whether every path from the owner's own entry to its exit passes through at least one of the group's `Wait()` calls — the same class of precision Phase 2 already has for `LL1002`'s loops. - Continued Phase 5 of the AST-to-CFG migration described in `docs/cfg-migration-plan.md`: `internal/frontend`'s parameter-consumption check for a cancel/group value passed directly as a same-package function argument no longer depends on source declaration order. Previously, `computeParameterConsumption` ran once per function in a single pass, so a multi-hop chain (`A(c){B(c)}`, `B(c){C(c)}`, `C(c){/* consume */}`) was only verified as deep as a later function's result happened to already be computed when an earlier caller needed it — the same 3-hop leak was caught when declared leaf-first and silently missed when declared caller-first, the more common style. `computeParameterConsumption` is now re-run for every function, in the same order, until a full sweep records no new result: a small interprocedural fixed point over per-function parameter-consumption summaries, not a single pass. `argumentConsumed` gained a third return value, `pending`, distinguishing "this same-package callee's result just isn't known yet, retry next sweep" from "this callee can never be resolved with confidence" (a different package, an interface method, a function value, a `...` spread); only the pre-pass, tracked by a new `inParamPrepass` builder flag, treats the former specially, leaving the dependency unresolved for this sweep rather than assuming transfer — the latter still falls back to the prior conservative "assume transferred" behavior immediately, on every sweep, exactly as before. Each summary is recorded via a monotone OR-merge (a result can only go from absent to known, or from known-false to known-true, never back), which is what bounds the number of sweeps and guarantees the fixed point is reached, including through cycles: a mutual- or self-recursive chain that never actually consumes the value converges to "not consumed" (a genuine leak, correctly flagged), and the same shape with a real base-case consumption converges to "consumed". `internal/frontend/frontend_test.go` now checks the previously order-dependent 3-hop chain in both declaration orders (both now fire `LL1001`), the matching non-leaking chain in both orders (neither fires), and both a non-consuming and a consuming recursive cycle, in place of the prior test that documented the caller-declared-first case as an accepted gap. No diagnostic verdict changed for any case that was already verified (the one-hop case, or a chain that already happened to resolve under the old declaration-order pass); this only extends verification to chains the prior single pass used to miss.
