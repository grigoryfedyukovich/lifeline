# Changelog

## Unreleased

- **Optimized — structural CFGs are built once per function body and reused (third F11 scaling tranche)**: parameter-effect inference, WaitGroup-`Done` inference, constructor-caller verification, and final cleanup/stop ordering all ask reachability questions over the same purely structural CFG. They previously rebuilt that graph and its call-site index independently, so one function could pay for the same AST-to-CFG translation several times before diagnostics were emitted. `internal/frontend.builder` now memoizes one immutable structural graph per `*ast.BlockStmt` and reuses it across those passes; the trusted lifecycle CFG used by `LL1002` remains separate because its context-dependent `EdgeTrustedStop` edges have different semantics. The cache is cancellation-safe: partial/cancelled graphs are never stored, and the prepasses now use `cfg.BuildContext` through the cache rather than the non-cancellable compatibility wrapper. A focused regression verifies that two consumers requesting the same body receive the same graph and call-site index. **Remaining F11 work:** the local SSA-like IR is still built unconditionally; group-specific body scans, coverage copying, loader importer reuse, and streamed `go list` remain open.

- **Optimized — constructor-return propagation no longer rescans the whole package (second F11 scaling tranche)**: `computeConstructorCallerConsumption` previously ran as repeated full sweeps over every selected function until no new pass-through wrapper was discovered. It also scanned every known returned-field binding/site for each candidate constructor call to find entries whose `site.fn` matched that callee. The frontend now maintains a callee-indexed `returnFieldsByFunc` alongside `returnFieldInfo`, evaluates every selected function once initially, and uses a reverse direct-call dependency worklist: when a function is newly recognized as forwarding a constructor-owned field, only callers of that function are re-enqueued. `appendReturnFieldSite` updates both indexes atomically and duplicate insertions do not grow either view. This preserves the existing arbitrary-depth/caller-first pass-through behavior while removing repeated package-wide constructor sweeps and binding-by-binding call matching. Existing field/constructor regressions and the broader frontend/CFG/local-SSA/model/engine suites pass under the Go 1.23 compatibility harness; a new index-invariant regression pins the dual-index maintenance. **Remaining F11 work:** structural-CFG reuse is addressed by the later entry above; the local SSA-like IR is still built unconditionally; group-specific body scans, coverage copying, loader importer reuse, and streamed `go list` remain open.

- **Optimized — parameter-effect fixed points no longer rescan the whole package (first F11 scaling tranche)**: `frontend.Build` previously recomputed `computeParameterEffects` and `computeParamDoneEffects` for every selected function on every fixed-point sweep. A caller-first delegation chain therefore required progressively more whole-package passes even though each summary depends only on its callees. The frontend now indexes reverse same-package call dependencies once (including the narrow single-assignment function-variable target shape already supported by `resolveCalleeFunc`) and solves the monotone equations with a worklist: every function is evaluated once initially, and only callers of a function whose summary actually grows are re-enqueued. Recursive/self-recursive SCCs converge naturally through queue edges; declaration-order semantics are unchanged. Existing multi-hop, recursion, may/must, WaitGroup-Done, and declaration-order regression suites pass under the local compatibility harness. **Remaining F11 work:** constructor-return propagation and structural-CFG reuse are addressed by the later entries above; the local SSA-like IR is still built unconditionally; group-specific body scans, coverage copying, loader importer reuse, and streamed `go list` remain open.

- **Fixed — configured timeouts did not interrupt frontend analysis (first F9 resource-control tranche)**: standalone previously passed its context only to `go list` and checked it between package jobs; once `loadOne` or `frontend.Build` started, a deadline could not stop the fixed points, AST walks, CFG construction, or the always-built local SSA-like IR. `go vet` treated `-timeout` as metadata only. `frontend.BuildContext` now carries cancellation through the fixed-point loops and builder traversals, `internal/cfg.BuildContext` and `internal/localssa.BuildContext` poll while traversing a function, standalone passes its work context through package loading and preserves diagnostics/coverage from functions completed before cancellation, and vet enforces the configured timeout as a per-package frontend deadline. The existing `Build` APIs remain compatibility wrappers using `context.Background()`. Timeout diagnostics are shared through `engine.TimeoutDiagnostic`, while run incompleteness remains independent of whether `LL9001` is hidden. New cancellation regressions cover CFG, local IR, and frontend interruption inside a large function. **Remaining F9 work:** parsing a single file and `go/types.Config.Check` are synchronous/non-cooperative, there are no node/edge/update or memory budgets, and a few helper scans only observe cancellation at the surrounding checkpoint; the timeout is cooperative, not a hard wall-clock guarantee.

- **Fixed — run status was derived from the filtered diagnostics, and coverage said nothing about approximation (audit finding F8)**: `engine.Analyze` created the truncation diagnostic `LL9001` and then filtered it by `ignore`, and `report.New` computed `incomplete` solely from the diagnostics that were left. With a truncated run and `ignore: [LL9001]` the engine removed the notice and the JSON bundle said `incomplete: false`: a machine-readable status defect, not a display preference. Separately, `Coverage` counted bindings, groups and goroutines but nothing about what was handed off, left unestablished or never looked at, so a run that verified a cancel call and one that merely passed it to unfollowed code printed the same summary.
  - **A run status independent of diagnostics.** `engine.Status` is computed from the program before any filtering, by `AnalyzeWithStatus` (`Analyze` stays as a wrapper that drops it). It carries `units` (discovered / analyzed / skipped, counting named functions and function literals, plus `excluded_files`), `incomplete` and `reasons` (`max_functions`, `timeout`), `unsupported`, `suppressed` and `assumptions`. Filtering cannot change it: ignoring `LL9001`, `ignore: all` and suppression comments all leave `incomplete` and the unit counts as they were, and only the `suppressed` counts record that something was hidden.
  - **Two dimensions, not one.** `incomplete` is a resource gap (a bound or a deadline: the results cover only part of the input). `unsupported` is a semantic gap (the results are real but rest on an approximation): goroutine targets that could not be inspected, cancel functions and groups handed off to code outside the owning function, and bindings discharged somewhere whose all-paths question has no answer. They are reported and counted separately; neither implies the other, and `incomplete: false` is documented as not meaning semantically complete.
  - **Reported everywhere.** JSON bundle: `status` plus `incomplete` (now `status.incomplete`, not a function of the diagnostics). SARIF: run properties `status` and `incomplete`. Text: a hidden truncation is still stated ("analysis incomplete (max_functions) ... results cover only part of the input") and a clean result says when it rests on approximations, hides findings, or excluded files. `report.New` and `report.Write` take the status.
  - **A separate policy.** `fail_on_incomplete` / `-fail-on-incomplete` and `fail_on_unsupported` / `-fail-on-unsupported` fail with `ci_exit_code` based on the status alone, so ignoring `LL9001` cannot be used to pass an incomplete run. `fail_on` is unchanged and still reads diagnostics.
  - **A standalone timeout is status too.** It is recorded as a `timeout` reason, and its `LL9001` notice now follows `ignore` like every other diagnostic instead of bypassing it; `fail_on_incomplete` still trips when it is hidden.
  - **vet exposes the status.** `go vet` shows only diagnostics, so the analyzer now returns a `*analyzer.Result` (coverage and status, as its `ResultType`) and `-lifeline.status-out=PATH` appends one JSON line per package. Note that `go vet` also analyzes dependencies for facts, so the file has a record for every package vet visited, not only the ones named; the package field identifies each.
  - **Honest counting.** A hand-off is counted only when it is all the evidence there is (not when the binding is also called, as in `return g.Wait()`), and a constructor whose callers in the package are checked at their own call sites (finding F2) is not counted, because that transfer is verified rather than assumed. A cancel function returned to a caller outside that tracking is counted.
  - **Measured**: finding counts are unchanged across all 111 pre-existing examples (56 before and after). Text output changes only by added status lines in 5 of them (3 with a hand-off note, 1 with excluded files, 1 with a hidden diagnostic); JSON gains `status` everywhere. Six standard library packages produce no diagnostics, and `net/http` plus `database/sql` report 863 of 863 units analyzed, 2 unsupported targets and 9 handed-off obligations.
  - **Not done**: the status does not count what it cannot see: wrapper functions not declared in configuration, unmodeled calls that never touched a tracked value, aliasing, package-level function literals, reflection. A zero is not evidence of their absence, and `docs/limitations.md` says so. There is no "insufficient coverage" threshold, only the two policies above. Frontend deadlines are now cooperative (see the F9 entry above), but parser/type-check calls and explicit work/memory budgets remain unresolved parts of F9. Standalone status is aggregated across packages; vet's is per package.
  - New tests: `internal/engine/status_test.go` (9: hiding `LL9001` keeps the run incomplete under three ignore settings, status is identical with and without filtering, hidden diagnostics are counted by mechanism and rule, bounded incompleteness is separate from semantic gaps, a fully verified run has an empty status, merging, timeouts, the policy reads only the status, literal units count), `internal/report/report_test.go` (7, including unsupported-only versus fully modeled input and SARIF), and `tests/integration/status_test.go` (7, through the real binary: standalone truncation with and without `LL9001`, unsupported-only versus modeled, every fail-policy combination and exit code, config-file keys, a hidden timeout, and `go vet` with the companion file). Three new examples back them (`status_fully_modeled`, `status_unsupported_only`, `status_truncated_unsupported`). Each mechanism (status derived from diagnostics, status gated on LL9001 surviving, a policy that ignores hidden truncation, an unrecorded timeout, no vet file, uncounted hand-offs) was broken in turn and a test failed for each.

- **Fixed — LL1005 pooled stop signals per function and ignored when a deferred call runs (audit finding F7)**: `computeOrdering` collected every stop signal in the function once, applied the pool to each joined group, and used one `deferOnlyStopSeen` flag for all of them. Nothing related a cancel function to a particular group's workers, so an independent goroutine using a deferred cancel made a finite, unrelated group look like it waited before its own signal; the defer-only shortcut also never looked at whether the group's own `Wait` was deferred, so `defer wg.Wait(); defer cancel()` (which cancels first at return and is safe) was reported as wait-before-stop. The message asserted "its workers' own stop signal" on evidence that never established it.
  - **Worker-to-group and worker-to-stop relations.** A group's workers are the `go` statements that call `Done` on it (or pass it to a function that does) and the `Go` calls of a `WaitGroup`/`errgroup`. Its stop signals are the cancel functions of the contexts those workers use, directly or through contexts derived from them (a worker using a context made with `WithTimeout(ctx, ...)` is stopped by `ctx`'s cancel too), plus any configured `stop_wrapper` call. A cancel function whose context no worker of the group uses is not its signal at all. This also finds the `WaitGroup.Go` form, which the old per-function `UsedByChild` flag never saw.
  - **Deferred execution is modeled as execution.** A deferred call runs at return, after all plain code, and deferred calls run in reverse registration order, with registration order read off the CFG: a deferred stop against a plain `Wait` is after it; a plain stop against a deferred `Wait` is before it; with both deferred, the one registered *later* runs first (`defer wg.Wait(); defer cancel()` is clean, `defer cancel(); defer wg.Wait()` is reported). Registration order the graph cannot prove withholds the claim. The old all-or-nothing deferred test on the binding is gone, along with `allCallsDeferred`.
  - **A group is reported only when every one of its stop signals is proven after the `Wait`.** The old rule reported when *any* signal was after it, so `cancel(); wg.Wait(); cancel()` and `defer cancel()` as a safety net alongside an explicit `cancel()` before `Wait` could be reported. A signal the analysis cannot place in the graph (inside a closure) withholds the claim.
  - **An assumed connection is said to be assumed.** A `stop_wrapper` names no context or worker, so `JoinGroup` gains `StopCorrelation` (`worker-context` or `assumed-wrapper`), the LL1005 message for a wrapper reads "the wrapper is assumed to be what stops this group's workers", and the evidence says "not verified". A context-correlated finding keeps the original wording, which its evidence now supports.
  - **Measured**: all 111 examples give 56 findings before and after, with one evidence string reworded (the `defer_cancel_before_wait` example, same finding); 15 standard library and `x/sync` packages (`net/http`, `database/sql`, `os/exec`, `testing`, `net/rpc`, `net/http/httptest`, `context`, `go/build`, `cmd/go/internal/work`, `os/signal`, `log/slog`, `archive/tar`, `internal/singleflight`, `net/http/pprof`, `golang.org/x/sync/errgroup`) produce no diagnostics before or after.
  - **Not done**: a worker that reaches its context another way (a struct field, a channel, a context created inside a named function body) is not recognized as using it, so such a group gets no cancel-based stop signal and is not reported (fewer findings than before, by design: nothing is asserted without a relation); stop mechanisms other than a cancel function or a configured wrapper (closing a channel) are not recognized; the relation between a `stop_wrapper` and a group is still only an assumption; the new relation is function-scoped, like everything here. All written up in `docs/limitations.md`.
  - New tests in `internal/frontend/stop_order_test.go` (6 tests, 30 cases): the acceptance matrix (13), two independent groups and signals (5), derived contexts (3), worker shapes (5, including a named worker and `WaitGroup.Go`), correlation reporting, and deferred stop wrappers (4). Against the pre-fix `frontend.go` all six tests have failing cases, covering contamination, defer order, multiple signals, the wrapper message and the `WaitGroup.Go` miss. Each mechanism (the worker-context relation, context derivation, deferred-versus-deferred registration order, every-stop-after, deferred stop against plain `Wait`, plain stop ordering) was removed in turn and a test failed for each; one mutation first appeared not to fail only because it did not compile, and was redone.

- **Fixed — interprocedural summaries could not tell cleanup from a hand-off, or a conditional from an unconditional (`LL1001`/`LL1003`, audit finding F6)**: whether a callee "consumed" a cancel function or group was one boolean (`Called || Escapes`, `Joined || Escapes`), and a positive answer was applied as a blanket ownership transfer at the call. So `func maybe(cancel context.CancelFunc, enabled bool) { if enabled { cancel() } }` called as `maybe(cancel, enabled)` erased the owner's obligation even when `enabled` is false; a helper that forwarded a group elsewhere and one that waited on it were the same fact; and a cancel call after an unconditional `return`, or inside a closure that never runs, counted as consumption.
  - **Explicit effects replace the boolean.** `model.ParamEffect` is a set of **may** / **must** / **returns** / **opaque**, computed per parameter on the callee's own control-flow graph from its entry: only a call some normal path can reach counts, and must means no path avoids every one (a deferred call covers every path that registered it). Hand-offs stay conservative: a returned value is `returns`, and a stored value, a use inside a literal that may run, or a pass to something not followed is `opaque`.
  - **Applied at the call instruction.** A must callee is a cancel (or `Wait`) at that call in the owner's own graph, so the owner's all-path check judges it: `defer always(cancel)` is clean, `if c { always(cancel) }` is reported (it was silent). A may-only callee is never a discharge: `maybe(cancel, enabled)` is reported as called on some but not every path, as is a group handed to a helper that waits conditionally. A helper-mediated join is now a join site, so `JoinedOnAllPaths` is established for it.
  - **Closes a documented gap**: `run(&wg, false)` with `if ok { g.Wait() }` inside was a known, tested false negative (`TestParameterPassing_GroupHelperConditionalWaitUnverifiedGap`). It is now reported (`..._GroupHelperConditionalWaitIsNotAJoin`). The literal argument is not evaluated, so the helper is reported whatever it is passed.
  - **Recursion**: a pass-through to a function in the same call cycle counts as a discharge only in a function that has a real one of its own, so `countdown(c, n-1)` that bottoms out in `c()` is must, a cycle with no real discharge stays a leak. The static call graph is built once per run for this.
  - **Exported and local effects have the same semantics, verified**: `FunctionFact.ParamConsumption` (a bare bool) is replaced by `ParamEffects`, `Input.LookupParamConsumption` by `Input.LookupParamEffects`, and a test exports a helper's effect and applies it through the lookup for seven helper shapes and three call shapes, requiring the same diagnostics as the same helper in the same package. The old boolean hook is still honored when no effect is available ("consumed" reads as opaque, "not consumed" as a checked absence).
  - **`version.FactVersion` bumped 4 -> 5.** The fact shape changed and the two are not interchangeable; facts from older builds are ignored, not reinterpreted. This is a compatibility break for cached vet facts.
  - **`Done()` gets the same distinction.** `ParamDoneCalled` (a bool) is replaced by `ParamDoneEffects` (may / must over reachable calls, through further same-package helpers), so a worker that calls `Done` only on some paths is not presented as an all-path guarantee. The Add/Done tally still counts a may-only worker as one `Done`: its only claim is an undercount, which holds even if every conditional `Done` fires, and an earlier version of this change that withheld the count lost a provable finding (`Add(3)`, one certain worker plus one conditional) before I measured it and reverted it. A `Done` inside a function literal is still not counted; exactly-once is not checked.
  - **Measured**: output across all examples is unchanged (56 diagnostics before and after), and 13 closure- and helper-heavy standard library packages (`net/http`, `database/sql`, `os/exec`, `testing`, `net/rpc`, `net/http/httptest`, `context`, `go/build`, `cmd/go/internal/work`, `os/signal`, `log/slog`, `archive/tar`, `internal/singleflight`) produce no diagnostics before or after, so no new false positives there. New true positives exist only where a helper is conditional or the call is.
  - **Not done**: a literal's own control flow is not folded into a helper's effect (a use inside a literal that may run is opaque, never must, so `defer func(){ cancel() }()` inside a helper is permissive); a conditional callee is never specialized on the arguments it was called with; exactly-once `Done` is not checked; cross-package callee effects reach only what the fact carries.
  - New tests in `internal/frontend/param_effects_test.go` (10 tests): the cancel matrix (20 cases) and group matrix (8), exported effect values (10), exported-versus-local equivalence (7 helpers x 3 call shapes), the legacy hook, `Done` effects (9), the upper-bound tally (6), the forwarding label, and the effect-set helpers. One existing test rewritten (the documented gap) and the Done lookups in `frontend_test.go` retargeted to effects. Seven mechanisms (blanket escape, reachability, dead closures, recursion, may-only handling, must establishment, helper joins as join sites) were each removed in turn and a test failed for each; two of those first appeared not to fail only because the mutation did not compile, and were redone.

- **Fixed — function literals were lifecycle boundaries without obligation records (`LL1001`/`LL1003`, audit finding F5)**: `collectBindings` stopped at every `*ast.FuncLit` and `Build` only enumerated `*ast.FuncDecl`, so a cancel function or join group created inside a closure was never judged: `go func() { _, cancel := context.WithCancel(p); _ = cancel }()` reported nothing, while the same two lines in a named function reported `LL1001`. Closures are where most realistic Go concurrency lives (goroutine bodies, callbacks, immediately invoked literals).
  - Every function literal is now an analysis unit with a stable identity following the toolchain's naming (`outer.func1`, `outer.func1.1`, `(*T).m.func2`), analyzed with the same machinery as a named function, including the F3 acquisition-relative path checks and the error guard. Findings are attributed to the literal and to the right line.
  - **Audit acceptance, each with a test**: moving code from a named function into a literal preserves findings (12 scenarios, each run as a named function and inside a `go` literal, an invoked literal, a `defer` literal, a callback and a stored-then-called literal, all required to match each other and an explicit expectation); defining a closure never discharges an outer obligation (`_ = func(){ cancel() }`, `var _ =`, a variable that is only ever blanked, and the same for `wg.Wait()`); nested goroutines keep correct attribution and are not reported twice.
  - **A literal owns only what it declares.** A cancel function or group declared outside the literal and merely assigned or started inside it is left to the enclosing function: judging it from inside would report uses the unit cannot see.
  - **No duplicate reports**: the enclosing declaration's walk already descends into closures for goroutine starts, so a literal unit carries only cancel and group bindings, with no goroutines, lifecycle summary or IR. Nested-goroutine output is identical before and after on the probe cases (loop two goroutines down, siblings, a group started in a nested goroutine).
  - **The bound covers literals**: `max_functions` now counts literals, after all named functions, so truncation drops closures first. `function_count` in reports, and the "analysis stopped after N of M functions" message, include literals. **This changes the reported number for any package that has closures.**
  - **Measured**: the original text output across all examples is unchanged (none declared a cancel or group inside a closure). On real-world closure-heavy code, `net/http`, `database/sql`, `os/exec` and `testing` from the standard library produce no diagnostics before or after, with the analyzed cancel-binding count rising by one: no new false positives there.
  - **Not done**: the audit's full "closure effects applied when invoked or transferred under a supported contract" model. A captured outer cancel or group used inside an invoked or transferred literal is still credited permissively and its all-path check stays unestablished (`func() { if c { cancel() } }()` is not reported); only never-run literals are excluded. Stored-then-called and callback shapes are not mapped to their call sites; package-level literals are not analyzed. All written up in `docs/limitations.md`.
  - New tests in `internal/frontend/closures_test.go` (11 tests). Against the pre-fix `frontend.go` the behavior tests fail; those that pin what must not regress (ownership of declared variables only, no duplicate goroutine reports, suppression, no extra records) pass on both. Each safeguard was also removed individually (ownership filter, never-run exclusion, dropping a literal's goroutines, counting against the bound) and a test failed for each.

- **Fixed — the suggested fix could produce invalid or lifetime-changing source (`LL1001`, audit finding F4)**: every short assignment with a blank cancel result got `; defer name()` inserted after it, without checking where the assignment sits. In `if ctx, _ := context.WithCancel(p); ctx != nil {` (and `for`, `switch`, type-switch and `else if` initializers) that is not even valid syntax; in a `for`/`range` body it parses but retains every iteration's context until the function returns; and for `context.WithCancelCause` the deferred call is missing its argument and does not compile. The diagnostic is unchanged in every case. The edit is now offered only when it is valid Go that preserves scope and lifetime.
  - **Withheld**, each with a test: assignments that are the init statement of `if`/`for`/`switch`/type switch/`else if`; anything inside a `for` or `range` body, however deeply nested through blocks, `switch` and `select`; a labeled statement; any function that uses `goto`; and a cancel function that takes an argument (`context.CancelCauseFunc`, or a configured wrapper returning `func(int)`).
  - **Still offered**: a standalone statement in a block, `case` body or `select` clause, including nested blocks outside any loop. A loop that comes *after* the statement does not matter.
  - **Name collisions**: the name was already checked against every identifier in the function; it now also records the name it picks, so two fixes in one function get `lifelineCancel` and `lifelineCancel2` instead of both using `lifelineCancel` (valid only by accident of redeclaration and shadowing). Locals, parameters, receivers, package-level names used in the function and a function named `lifelineCancel` are covered by tests.
  - **Measured**: of the 108 examples only `lost_cancel` and `custom_context_wrapper` emit a fix, and both are unchanged.
  - **Not changed**: an edit that rewrites an initializer, or releases per iteration (extracting a helper), is a separate feature with its own scope-preservation tests, as the audit says. The `goto` rule is deliberately coarse. Function literals still get no analysis, so no fix (audit finding F5).
  - New tests in `internal/frontend/fix_validity_test.go` apply every emitted fix, each alone and all together, parse and type-check the result, and also assert whether a fix must be offered, so a pass cannot come from fixes silently vanishing: scope and lifetime shapes (24 cases), identifier collisions (9), distinct names across fixes, configured-wrapper result shapes (cancel first, extra error result, cancel with an argument), and the two examples that emit fixes. Against the pre-fix `frontend.go` the invalid or lifetime-changing cases fail; each of the five safety checks (parent statement, loop/label ancestor, `goto`, cancel signature, name bookkeeping) was also removed one at a time and a test failed for each.

- **Fixed — error-returning factories were flagged on the error branch (`LL1001`/`LL1003`, audit finding F3, "guarded summaries")**: `ctx, cancel, err := Make(p); if err != nil { return err }; defer cancel()` warned, because the `return err` path reaches the exit without a cancel call even though the factory failed and created nothing. The same false positive hit every caller of an error-returning constructor, `h, err := New(p); if err != nil { return err }; defer h.cancel()`, the most common shape of a returned handle. When the factory call also assigns an error, the cleanup check now rules out the branch on which that error is non-nil.
  - Still warns, each covered by a test: no check at all; an unrelated early return after the check; a cancel only under an unrelated `if`; a defer registered after such a return; a check that is about a *different* error because `err` was reassigned first; and a check whose condition does not imply an error on the ruled-out branch (`err != nil || c`, `err == nil && c`).
  - **The factory's contract is assumed, not verified**: a wrapper returning a live cancel function together with a non-nil error would leak on the excused path. For a cancel binding, an `error-guard` evidence line is added whenever the guard is what turns the verdict; a constructor caller has no evidence slot yet, and the gap is written up in `docs/limitations.md`. Verifying the contract from the factory's own return statements (a true guarded summary) is not done.
  - Conservative about the error variable still holding the factory's result: any other assignment between call and check, a check in a loop that assigns it, a closure that assigns it, or taking its address each disqualify the check (status quo for that check, not a new finding). Unmodeled forms: `switch` on the error, `errors.Is`/helper predicates, aliases, `goto` back-edges.
  - Implementation: `model.CFG.ReachableAvoidingEdges` (edge-skipping reachability; `ReachableAvoiding` now delegates to it), `builder.errorBranchSkipper` (matches the `if` condition's true/false edges by span), and a `skipEdge` parameter on `liveExitReachable`. `cancelState` gains `errObj`.
  - Examples: `examples/context_wrapper_error_checked` (clean) and `examples/context_wrapper_error_early_return` (still `LL1001`), both in the integration table. Tests in `internal/frontend/error_guard_test.go`: the wrapper matrix (idiom, `err == nil`, else-return, negation, `&&`/`||`, if-init form, and the still-warns cases above), the evidence line, constructor callers (cancel and group), and a mutation check that the false-positive cases fail with the guard disabled.

- **Fixed — cleanup obligations were checked from function entry, not from where they begin (`LL1001`/`LL1003`/`LL1004`, audit finding F3)**: `CalledOnAllPaths`/`JoinedOnAllPaths` asked whether every path from the function's entry reaches a cleanup call, so a path that never created the resource was counted as a cleanup failure. `if enabled { _, cancel := context.WithCancel(p); defer cancel() }` warned, as did an early return placed before the acquisition, a group started only inside a branch, and a constructor called only inside a branch. The check now starts at the acquisition (the `WithCancel` call), at each worker start (`Add`/`Go`), or at the constructor call, and asks whether some path from there reaches the function's exit without a cleanup call.
  - Audit acceptance matrix, all verified: conditional acquire-and-clean is clean; conditional cleanup after unconditional acquisition warns; early return before acquisition is clean; early return after acquisition warns. Repeated for groups and returned handles.
  - **Deferred calls are handled as what they are.** A `defer` runs at exit on every path that registered it, before or after the origin, so `defer wg.Wait()` written above the `wg.Add(1)` still covers it, while a `defer` registered only after an early return no longer covers the path that returned first (previously the defer's position in the entry block made such cases coincidentally clean or coincidentally flagged).
  - **Group `Wait()` calls count anywhere on the path, cancel calls must follow the creation.** A `Wait()` before a later `Add()` is the second-round-reuse case that `UnjoinedRound` already reports with its own message; counting it in the path check too produced the wrong advice ("add a defer"), so it is left to `UnjoinedRound`.
  - **An origin that cannot be placed is left unestablished, never guessed.** A worker start inside a closure is not part of this function's CFG; `JoinedOnAllPaths` then stays nil (treated as "not established") instead of falling back to the entry-based question that caused the false positive.
  - **Measured delta**: the original diagnostics across every `examples/` package are unchanged in count and location; only the evidence wording of the four path-based findings changed ("some path from this cancel function's creation..." / "...from the point a worker is started..."). No existing fixture depended on the entry-based false positives. Earlier in this series, the F2 change was re-measured the same way and moves exactly the four `constructor_*` examples.
  - **Error-returning factories are handled in the same change** (see the next entry). Not changed: reassignment and repeated acquisition in a loop are judged per acquisition site at block granularity, not with per-event state. `docs/limitations.md` corrected a long-standing claim here: `ctx, cancel := WithCancel(p); if unrelated() { return }; defer cancel()` was documented as a safe idiom that false-positives, but it leaks on the early return and firing is correct.
  - Constructor callers get the same treatment: the obligation starts at the constructor call, so a caller that only calls the constructor inside a branch, or returns before it, is clean, while a return after the call warns.

  - **Important architectural caveat, surfaced during this work and documented in `docs/limitations.md`**: this fact is not a drop-in analog of `ParamConsumption`/`ParamDoneCalled`. Those two answer a question purely about the *callee's* own body, true or false independent of any specific caller — exactly what a fact can answer once and have every future importer reuse. `ReturnFieldSites`' consumer-side check instead asks whether the *caller* consumes what it received, and for a same-package constructor that verdict feeds back into the constructor's own diagnostic because both functions are analyzed in the same `Build` call. A cross-package constructor's package has already been analyzed and its diagnostics already finalized by the time an importing package is analyzed — facts flow from a dependency to its dependents, never backward — so a caller-side finding cannot reach back and revise that already-reported verdict. This extension does what was literally asked (removes the mechanical `types.Object` dependency, lets the caller-side check run at all for a cross-package callee, records the verdict the same way a same-package one is), but does not and structurally cannot make cross-package constructor leak detection as complete as the cross-package parameter-passing and named-worker-`Done` extensions already are.

  - New tests: `internal/model/cfg_algorithms_test.go` (`ReachableAvoiding` on linear, self-avoiding, and diamond-branch CFGs), `internal/cfg/cfg_test.go` (`CallSite` recording for bare/defer/go/assignment-RHS/if-init calls, nested-call exclusion, same-block index ordering, cross-branch block separation), `internal/engine/engine_test.go` (each new `LL1003`/`LL1004` message variant, `LL1005`, and the nil-`JoinedOnAllPaths` safe-default), and `internal/frontend/frontend_test.go` (count mismatch, the paired idiom including an unresolvable-loop-count case that must stay silent, join-not-on-all-paths, and stop-after-wait including an "unrelated cancel not captured by any goroutine" false-positive guard). `JoinObligation`/`Ownership` (Phase 3's still-unwired dataflow lattices) remain exactly as unwired as before: this went a narrower, more direct route instead, since those two lattices' generic forward-dataflow shape didn't fit these two reachability questions noticeably better than a direct graph check does. No diagnostic verdict changed for any group that was already correctly handled by the old flat check (fully joined with no CFG or count issue, or genuinely never joined at all); this only adds findings the old check structurally could not distinguish from "everything's fine".
- Continued Phase 5 of the AST-to-CFG migration described in `docs/cfg-migration-plan.md`: `internal/frontend`'s parameter-consumption check for a cancel/group value passed directly as a same-package function argument no longer depends on source declaration order. Previously, `computeParameterConsumption` ran once per function in a single pass, so a multi-hop chain (`A(c){B(c)}`, `B(c){C(c)}`, `C(c){/* consume */}`) was only verified as deep as a later function's result happened to already be computed when an earlier caller needed it — the same 3-hop leak was caught when declared leaf-first and silently missed when declared caller-first, the more common style. `computeParameterConsumption` is now re-run for every function, in the same order, until a full sweep records no new result: a small interprocedural fixed point over per-function parameter-consumption summaries, not a single pass. `argumentConsumed` gained a third return value, `pending`, distinguishing "this same-package callee's result just isn't known yet, retry next sweep" from "this callee can never be resolved with confidence" (a different package, an interface method, a function value, a `...` spread); only the pre-pass, tracked by a new `inParamPrepass` builder flag, treats the former specially, leaving the dependency unresolved for this sweep rather than assuming transfer — the latter still falls back to the prior conservative "assume transferred" behavior immediately, on every sweep, exactly as before. Each summary is recorded via a monotone OR-merge (a result can only go from absent to known, or from known-false to known-true, never back), which is what bounds the number of sweeps and guarantees the fixed point is reached, including through cycles: a mutual- or self-recursive chain that never actually consumes the value converges to "not consumed" (a genuine leak, correctly flagged), and the same shape with a real base-case consumption converges to "consumed". `internal/frontend/frontend_test.go` now checks the previously order-dependent 3-hop chain in both declaration orders (both now fire `LL1001`), the matching non-leaking chain in both orders (neither fires), and both a non-consuming and a consuming recursive cycle, in place of the prior test that documented the caller-declared-first case as an accepted gap. No diagnostic verdict changed for any case that was already verified (the one-hop case, or a chain that already happened to resolve under the old declaration-order pass); this only extends verification to chains the prior single pass used to miss.
- Completed Phase 4 of the AST-to-CFG migration described in `docs/cfg-migration-plan.md`, narrowly (the termination dimension only): the cross-package `go vet` fact (`FunctionFact`, `analyzer/analyzer.go`) now carries `LoopUnresolved`, the exporting package's own CFG/SCC-derived `LL1002` verdict for its function (`internal/engine.UnresolvedLoop`), alongside the prior flat booleans. Fact schema version bumped 2 -> 3 (`version.FactVersion`); an older fact is simply unavailable to a newer binary rather than reinterpreted, since `ImportObjectFact` requires an exact version match. This closes a real gap Phase 2 left open: a cross-package goroutine target previously fell back to the old flat evidence check, which has the same "evidence anywhere in the body suppresses everything" flaw Phase 2 fixed for same-package/closure targets — concretely, two nested unconditional loops where only the inner one has a `break`, exported across a package boundary, was a genuine false negative even after Phase 2 landed, since the exported fact only had one shared `HasReturn` per function and the inner loop's break flattened into it. `tests/testdata/facts/mixed_consumer` and `TestVetCrossPackageFactCatchesMixedResolutionLoop` hold this as a permanent regression fixture. `JoinObligation`/`Ownership` (Phase 3's still-unwired dimensions) are not exported as facts yet; this is a narrower slice of Phase 4's full "effect summary" scope (`docs/cfg-migration-plan.md` §7) than the doc eventually envisions. No diagnostic verdict changed for standalone mode or same-package/closure vet targets: every example, golden file, and non-fact integration test remains byte-identical to before this change.
- Started Phase 3 of the AST-to-CFG migration described in `docs/cfg-migration-plan.md`: added `model.Solve` (`internal/model/dataflow.go`), a generic forward-dataflow worklist solver over `model.CFG`, and three lifecycle-specific lattices built on it (`internal/engine/dataflow_lattices.go`): `StopCapability`, `JoinObligation`, `Ownership`. Only `StopCapability` is wired to real CFG structure end to end (a block's own trusted-stop/return/panic edge — a local check, not global reachability, which the test suite confirms would be too permissive: it would mark every branch of a select loop "resolved" just because a sibling branch returns) and exposed via a new `lifeline -dump facts [-dump-format text|json]` command, per the migration doc's section 8.2. `JoinObligation` and `Ownership` are demonstrated only against synthetic fixtures; wiring them to real WaitGroup/errgroup/cancel bindings is tracked as remaining work in `docs/roadmap.md` and `docs/cfg-migration-plan.md`'s status header, and `-dump facts`'s `join` field says so explicitly (`"analyzed": false`) rather than showing fabricated data. "Worker exit state" is deliberately not reimplemented as a forward-dataflow fact, since Phase 2's SCC/reachability analysis already answers that (backward) question correctly. This is purely additive: no diagnostic verdict changed, and every example, golden file, and integration test remains byte-identical to before this change.
- Completed Phase 2 of the AST-to-CFG migration described in `docs/cfg-migration-plan.md`: `LL1002`'s verdict is now computed from `internal/cfg`'s control-flow graph rather than the flat per-body evidence booleans introduced in Phase 0/1. An unconditional loop fires only when it forms a reachable, persistent (cyclic) strongly-connected component with no edge leaving it that can reach the function's exit block (`internal/engine/cfg_verdict.go`), and each such component is judged independently. This closes the residual false negative documented since loop-scoping: a goroutine with two separate unconditional loops where only one has its own exit (e.g. `for { for { break } }`) is now correctly still flagged for the other — `tests/differential/cfg_ast_test.go`'s `TestFixed_NestedLoopsMixedResolution` (previously a "known false negative" fixture) now passes as a fixed regression test. `break`, `continue`, and `goto` (including labeled forms) are resolved to their exact targets under Go's own grammar rather than approximated. A configured stop-wrapper call and context-delegation-to-a-called-operation are now represented as a trusted edge straight to the function's exit (`EdgeTrustedStop`) via a predicate `internal/frontend` derives from config and passes into `internal/cfg`, which itself remains free of any config or tracked-context awareness. This verdict applies wherever a CFG was built; a cross-package goroutine target resolved through a `go vet` fact still falls back to the older flat check, since facts do not yet carry CFG-derived information (tracked as remaining work in `docs/cfg-migration-plan.md`). Every example, golden file, and integration test produces byte-identical output to before this change except the one case it was meant to fix.
- Started the AST-to-CFG migration described in `docs/cfg-migration-plan.md`, Phase 0 and Phase 1: added `internal/cfg`, a parser-independent control-flow-graph builder (`if`/`for`/`range`/`switch`/`select` branches, loop back-edges, `break`/`continue`/`goto` resolved to their real targets under Go's own scoping, `return`/`panic` routed to exit), plus text and DOT renderers exposed as `lifeline -dump cfg [-dump-format text|dot]`. `tests/differential/cfg_ast_test.go` added explicit regression fixtures per Phase 0.
- A configured `start_wrapper`'s entry point is now found by type rather than by requiring an inline closure: `Launch(myWorker)` where `myWorker` is a top-level declared function is now recognized, reusing the same same-package/cross-package resolution `go` statements already get. An inline closure is still preferred when both are present in a call's arguments, matching prior priority.
- A `context_wrapper`'s context and cancel-function results are now identified by their static types instead of by fixed position (0, 1). A wrapper may now return them in either order and may return additional results (e.g. a trailing `error`) alongside them without being mistracked.
- Generated files (carrying the standard `// Code generated ... DO NOT EDIT.` marker) are now automatically excluded from analysis in both standalone and vet mode. A new `ignore_paths` config list additionally excludes files by glob pattern (`filepath.Match` semantics, matched against both the relative path and the base filename).
- A specific finding can now be suppressed inline with a `//lifeline:ignore` (optionally `//lifeline:ignore LL1001,LL1002`) comment, matched against the diagnostic's own line and every evidence span's line so it can go on whichever line most naturally names the construct.
- `LL1002` loop-exit evidence (`break`, `return`, a `select` case, a stop-wrapper call, a delegated context) is now scoped to the specific unconditional loop it is lexically part of, instead of being treated as evidence for every unconditional loop anywhere in the same goroutine body. Concretely: an unrelated `break` inside a `switch` or `select` nested in an infinite loop no longer suppresses a finding about that loop (an unlabeled `break` only exits the nearest enclosing loop/switch/select under Go's own rules, so it shouldn't have counted); a `return` before an infinite loop starts no longer suppresses a finding about a loop it can't help exit; a bare (non-`select`) range over a channel no longer suppresses a finding about a separate, unrelated infinite loop elsewhere in the body. Labeled `break` is now matched to the loop it actually targets rather than accepted for any loop in the body. See `docs/limitations.md` for the one remaining case this does not close: a goroutine with two separate unconditional loops where only one has its own exit still suppresses the finding for the whole goroutine, since exit status is tracked per goroutine, not per loop.
- Standalone-mode text/JSON/SARIF output no longer collapses three different situations into the single string `no lifecycle diagnostics`. It now distinguishes: nothing lifecycle-relevant was recognized at all (`no recognized lifecycle constructs`); everything recognized was compliant (`no lifecycle diagnostics (checked N cancel binding(s), M goroutine(s), K group(s))`); and everything recognized was compliant except for goroutine targets whose bodies could not be inspected, which are now listed by file:line and reason instead of being silently absent. This also means a standalone run that hits a cross-package goroutine target (which standalone mode cannot resolve via facts, unlike `go vet`) now discloses that gap instead of reporting an indistinguishable clean result. JSON/SARIF gain a `coverage` object with the same counts. See `docs/limitations.md` for exactly what the new counts do and do not cover — in particular, a call to an unconfigured wrapper function still contributes nothing to any of these counts, since no binding is ever created for it to summarize.
- Fixed a false lifecycle claim: cross-package `go vet` goroutine targets no longer inherit the caller's locally-available context names into `LL1002`'s "available cancellation source" evidence. The target function's actual parameters are unknown to the imported cross-package fact, so asserting a caller-side context as available to it was ungrounded and could point at a context the target never receives.
- Raised minimum Go version to 1.25.0 (reversing the prior "lowered to 1.22" change) and upgraded `golang.org/x/tools` (v0.22.1 -> v0.49.0) and `golang.org/x/sync` (v0.7.0 -> v0.22.0). This is a breaking change for anyone building with Go 1.22-1.24; there is currently no known `x/tools` version that satisfies both the old and new protocol.
